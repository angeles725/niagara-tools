### Changed — mcp-n4 reads histories four at a time and refuses a Spyder instance write on a faulted component

- `n4_histories_audit`: the per-history record counts, and the window and count reads of `flat=true`, run four at a
  time instead of one by one (issue #906). The reply is the same: each list keeps the order of the history
  extensions, and `count_reads`, `flat_reads`, `requests`, `elapsed_ms` and the failure notes mean what they did
  (the failure named is the first in extension order). The gain is not measured on a live station.
- `n4_invoke_action` `writeDeviceInstance` is refused at the dry run when the Spyder's `status` holds the fault flag
  (issue #927). The error names the component and its `faultCause`, says the write would end in the BOX error
  `raise() failed. Cannot find vmUuid` and that the controller would not be written, and no token is issued.
  Before, the dry run gave a token and the batch ended in doubt. A down or disabled Spyder still plans as before.
- Skill hard rule and METHODOLOGY §3: `MCP request timed out` is "unknown", never a failure; run `n4_list_batches`
  and read back before any retry, never resend the token (issue #925). METHODOLOGY §3 also explains the BOX error
  `raise() failed. Cannot find vmUuid`.
- Not done: a server call budget under the client's 60 s limit (rest of #925), the override audit (#908) and the
  combined min / max / count read and the progress lines of #906.
