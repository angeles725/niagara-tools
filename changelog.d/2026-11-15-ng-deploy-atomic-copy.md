### Fixed — ng-deploy: the copy is all-or-nothing
- Every jar of the mode is copied to `<jar>.ng-deploy-new` beside its target; then the jars the station holds are moved aside to `<jar>.ng-deploy-old`, the staged jars are renamed in, and the ones aside are removed. Each step is a rename within the modules directory, so a jar is replaced whole or not at all. Before: the rt jar was copied, then the ux jar, and a failure on the second left one new jar and one old with `copy failed for <ux jar>` as the only word.
- A step that fails is undone from the jars moved aside, with or without `--no-backup` (the backup of the run is not read): every jar aside is moved back, bytes and mode, and a new jar the station did not have is removed. Exit 40 then reads `copy failed for <jar>[: <reason>]; nothing was replaced: the station holds the jars it held before the deploy` (a jar that could not be staged or moved aside, or the first rename in), or `...; what was already replaced was put back: the station holds the jars it held before the deploy` (a later rename in).
- The one way left to a mixed pair is a jar aside that cannot be moved back. Exit 40 then says what each jar is and names the file that still holds the previous bytes, which is left in place: `...; the station does NOT hold the jars it held before the deploy: <jar> is the NEW jar and the previous one is in <jar>.ng-deploy-old (<reason>), <jar> is the previous jar; put each named .ng-deploy-old file back under its jar name before the station restarts` (also `<jar> is MISSING and the previous one is in ...`, and `<jar>, which the station did not have, could not be removed (<reason>) and must be removed`).
- Files of a killed run: a stale `.ng-deploy-new` is written over. A stale `.ng-deploy-old` beside its jar is removed. A stale `.ng-deploy-old` whose jar is missing may be the only copy of the previous jar, so the deploy stops before copying anything, exit 40 `copy failed for <jar>; <jar>.ng-deploy-old is in the station and <jar> is not: a deploy that was killed left the previous jar under that name; rename it back to <jar>, or remove it, then deploy again (nothing was copied)`.
- After a deploy, and after a failure that was undone, no `.ng-deploy-new` or `.ng-deploy-old` file is left. A finished copy that cannot remove a file aside still succeeds, with `[ng-deploy] WARN the jars are copied, but <jar>.ng-deploy-old (the previous jar) could not be removed: <reason>; the next deploy removes it`.
- Consequences of renaming instead of writing into the existing jar: the modules directory itself must be writable (a read-only directory holding writable jars used to deploy; it is now exit 40 with nothing replaced), a read-only jar in a writable directory is now replaced, and a jar that was a symbolic link is replaced by a regular file. A replaced jar keeps the mode the station's jar had.

### Fixed — ng-deploy: a record that cannot be written stops the deploy before the copy
- After the checks and before the copy, a `.last-deploy-sha` that is a directory or cannot be opened for writing, or a working directory that takes no new file when there is no record yet, is exit 10 `the deployed commit cannot be recorded in .last-deploy-sha (cannot write <path>: <reason>); nothing was copied (fix the file, or SLOTOMATIC_DETECTION=off makes the record optional)`. Before: the jars were copied first and the same condition was exit 41. The look writes nothing: an existing record is only opened, and a file it had to create is removed again.
- Exit 41 stays for what can only be known after the copy: `git rev-parse HEAD` failing or printing no full commit id, and a record that could be written before the copy and no longer can. With `SLOTOMATIC_DETECTION=off` nothing is looked at and the record stays best effort, as before.

### Fixed — ng-deploy: a recorded commit git does not know is no longer a silent fallback
- A `.last-deploy-sha` that holds a full object name `git cat-file -e <id>^{commit}` does not accept (a commit of another clone, a history rewritten since) gets `[ng-deploy] NOTICE: .last-deploy-sha names a commit git does not know; annotation changes are looked for since HEAD~1 only` on stderr, and in strict mode (`--strict-slotomatic` or `SLOTOMATIC_DETECTION=strict`, without `--with-slotomatic`) the deploy stops with exit 15 `annotation change detection could not run; ...`, as it does for a malformed record. Before: the diff started at `HEAD~1` without a word and strict mode passed. A change the `HEAD~1` diff does show is still reported as a change.

### Changed — ng-deploy: a flag wins over the env file, and the env file cannot skip the gate or the backup
- An option a flag set on the command line is no longer replaced by the option variable of the same name in the env file: `--mode C` with `MODE=B` in the file deploys mode C, `--keep 1` with `KEEP_N=4` keeps one backup, `--full-backup` with `FULL_BACKUP=0` backs the whole directory up, and a switch flag (`--no-deploy`, `--with-slotomatic`, `--strict-slotomatic`, `--first-deploy`, `--accept-lossy`, `--no-gate`, `--no-backup`) is not undone by a `0` in the file. Before: the file was read after the flags and silently replaced them. Without the flag the env file still sets the option, as before, and the commands the deploy runs still see the value the deploy settled on.
- `NO_GATE=1` or `NO_BACKUP=1` in the env file (any value bash read as 1) is exit 10 before anything runs: `[ng-deploy] ERROR env file <path>: line <N>: NO_GATE would switch the verify-module gate off, which an env file may not do: give --no-gate on the command line` (`NO_BACKUP` ... `the backup` ... `--no-backup`). With the flag given the key is accepted. Before: the key switched the gate or the backup off without a word. **An env file that carries either key must drop it and the deploy command must pass the flag.** `0`, an empty value and any other number leave the step on and are read as before.
- The flags and their option variables are one table (`go/internal/ngdeploy/optiontable.go`).
