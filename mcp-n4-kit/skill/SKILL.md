## Resolve the kit (do this first)

`KIT` = the `mcp-n4-kit` directory: it holds `METHODOLOGY.md` and `README.md`; the server it launches is the Go binary `$KIT/../go/bin/mcp-n4` (the only server since S17). Resolve once:
1. `$MCP_N4_KIT` if set and it contains `METHODOLOGY.md`.
2. Else the default: `/home/cristian/modulos_niagara_n4/niagara-tools/mcp-n4-kit`, the author's checkout on the primary machine (confirm `METHODOLOGY.md` exists). The installed launcher is a copy under `~/.claude/skills/`, so its own location says nothing about the kit; on any other machine or checkout set `MCP_N4_KIT` to the `mcp-n4-kit` directory.
3. Else STOP searching and say so plainly: "the mcp-n4 kit is not on disk at <path checked>". A checkout on another branch may lack `mcp-n4-kit/`; never switch a shared checkout's branch to get it. Offer the operator one of:
   - a worktree of `origin/main`: `git -C <niagara-tools checkout> fetch origin && git -C <niagara-tools checkout> worktree add <path> origin/main`, then `MCP_N4_KIT=<path>/mcp-n4-kit`;
   - an installed copy they already have (set `MCP_N4_KIT` to it).
   Ask before creating the worktree.

Then read `$KIT/METHODOLOGY.md` FIRST and follow its session checklist.

## Register the server

Follow `$KIT/README.md` ("Running the server", "Getting the kit and registering it per project"). Register the server once in the project's `.mcp.json` rather than driving stdio by hand. Launch the Go server `$KIT/../go/bin/mcp-n4` (absolute path; build it with `cd $KIT/../go && go build -o bin/ ./cmd/mcp-n4` if it is missing). The operator, not the model, chooses stations, credential env prefix, TLS policy and timing (`--station NAME=https://…`, `--credential-env`, `--insecure-tls NAME`, `--load-wait`, `--http-timeout`, `--auth-cooldown`), and where each station keeps its `config.bog` (`--station-home NAME=PATH`, so `n4_save_station` can prove persistence). Writes need `--allow-writes` plus at least one `--write-scope`; the default is read-only. A tier B or C station (METHODOLOGY section 5) also needs the operator's `--allow-tier-b NAME` / `--allow-tier-c NAME`, given only after the PoC or probe that tier requires. If no station is configured, stop and tell the operator which flag is missing.

## Before acting on an operator's hand edit

Before step 5 (and before relying on anything the operator wrote by hand or says is done, e.g. "ya lo hice"), read the value back live (`n4_read_slots`) and compare it with the intended value; never trust the confirmation alone. Evidence: `hmiPanelAddress` typed as 192.168.1.140 instead of .40, caught only by a live read-back. `[ev: external retro niagara-research/retros/2026-10-06-panccadia-comppan-hmi-support.md Δ3]`

## Session checklist (full detail in METHODOLOGY section 4)

1. `n4_describe_session`, `n4_connect` to a configured station; confirm the real station name, `version` and `tier`. With `tier_writes: refused`, plan with dry runs only (they carry `tier_gate`) and give the operator the refusal's routes.
2. "How is the station?" (state, CPU and memory, how many points and how many are down or stale, drivers, licence capacity): `n4_station_health` FIRST, one call; then drill into what it names (`not_ok` paths with `n4_read_slots`, a network with `n4_inventory`). Read each section on its own: one with `error` failed while the others answered; `truncated` cut the `not_ok` list only (`not_ok_count` is whole), `rows_truncated` makes the counts lower bounds; a status whose only flag is `null` (a point with no value, e.g. an unlinked input) is not a fault: it is counted in `null_only` and never listed in `not_ok`, and `ok + null_only + not_ok_count = total`; `null` beside another flag is not ok. `capacity: null` means the capacity could not be read (see `capacity_note`: the user may not read spy pages, or the page has no Global Capacity table on this version), NOT zero usage and NOT "no limit": say it is unknown and offer the Workbench Resource Manager view; `unlimited: true` is the station showing no limit for that resource. Two counts sit side by side in `capacity.resources`: `used` is the licence's own tally, the number to quote against `limit` for licensing ("points consumed"), and `live` is what the station really holds now (networks, devices, and `points.proxy`: a licence counts proxy points, not every control point in `points.total`). The tally only grows until a capacity recount or a station restart, so with `may_be_inflated: true` say that `used` may overstate and give `live` beside it; `capacity_truncated: true` means resources may be missing from the list. `license` is the licence in short: `licenses` with `valid` and `days_left` (from the station's date), `nearest_expiry`, `expired` and a `warning` when the nearest expiry is 60 days away or fewer, a licence is not reported valid, or an expiry could not be read; report a `warning` to the operator unprompted, and treat `license.error` as "the licence was not read", never as "no licence"; `n4_license_info` has the detail (certificates, features, SMA facts). Inventory or wide reads: `n4_inventory` / `n4_bql_query` FIRST (METHODOLOGY section 7); `n4_navigate` (optional `types` filter, which also keeps subtypes: `history:HistoryExt` finds every history extension) / `n4_read_slots` only for targeted components. History records: `n4_read_history` (a `history_id` such as `/MyStation/MyPoint`, or the extension's `ext_ord`) returns the last records newest first with `total_records`; use it to prove a history collects (an extension status `{ok}` proves it runs, not that records exist), and when it names a history it cannot read, list the ids with `n4_bql_query` `select historyConfig.id from history:HistoryExt`. Px graphics are files: `n4_list_px_views`, then `n4_px_summary` / `n4_read_file` on the `px_file` (METHODOLOGY section 9). Diagnostics are spy pages: `n4_spy_page` (empty `path` for the index, then a `links[].path`) returns a page's tables as data; it only reads (the `actions` a page lists are never invoked), needs a station user allowed to read spy pages (`status: forbidden` otherwise), and its tables are the station's own layout, which differs between Niagara versions: read them as found, never by a fixed row position. "Which licence, until when, certificates, SMA?": `n4_license_info`, one call (host id, certificates, licences with `days_left`, brand, owner, project, `nearest_expiry`, `expired`, the feature list; `feature` narrows it). Its `days_left` counts from the STATION's date (`station_date`), never this machine's; `null` means unknown or `never`, not zero. A licence or certificate with `valid: false` carries `state` (the page's own word): report it as not valid, whatever its date. An `expires` that is neither `never` nor a date comes back as written with `days_left: null` and is counted in `note`: say the expiry could not be read, never that it does not expire. A string ending in `...[cut]`, `attributes_truncated`, `sma_truncated` or a `*_count` above the list length mean the reply was bounded: read the page with `n4_spy_page` for the rest. `maintenance` reports only what the licence states: `sma_attributes` (per feature, its `sma.*` attributes), `sma_exempt_features` (the features with `sma.exempt=true`: each exempts that one feature only, so never say "the licence is SMA exempt") and a maintenance feature if any; its `expires` is `null` unless a local licence file states a `maintenanceExpiration`, because the page has no SMA end date: never present a licence expiry as the SMA end date, say the licence does not state it. When a licence was generated (`generated`), its `version` and that SMA date exist only in the licence files of the installation, so they appear only when the server was started with `--niagara-home NAME=PATH` for that station (an installation reachable from this machine); otherwise they are omitted and `generated_note` says why: tell the operator they are not available remotely instead of guessing a purchase date. A `status` other than `ok` (`forbidden`: the user may not read spy pages) means the licence was NOT read, not that there is none. A read or client expected to exceed ~1 min writes progress to a file and reports counts; never rely on stdout piped through `tail`.
3. Write tools with `dry_run=true` (the default); show the plan to the human.
4. After approval, repeat with `dry_run=false` and the `confirmation_token`. The token is bound to the plan including its warnings (a create's "name is already taken" note): a re-used create token, or a name taken after the dry run, is refused as a plan mismatch; redo the dry run.
5. Read the verdict; `n4_find_dangling_outputs`; `n4_save_station` with persistence evidence.
6. Keep every `batch_id` (`n4_list_batches` lists them, newest first).
7. Close with the session retro: call `n4_session_retro_draft` (or run `$KIT/../go/bin/retro-draft --write --station NAME --state-dir DIR`), review the candidate deltas, keep or edit them (or leave the honesty line `no new deltas`). Propose, never apply; stage issues only by hand.

## Hard Rules (non-negotiable)

- Never write without showing the dry-run plan to the human first.
- No credentials in tool arguments or chat; they come from the operator's environment.
- Never retry a failed login: 5 failures in 30 s lock the account. On a 401, have the operator check the user's Authentication Scheme Name = `HTTPBasicScheme`, then the password.
- Report `partial`, `mismatch`, `failed`, `unverified`, `in-doubt` and `persisted: unknown` exactly as returned; never call them success. A `partial` rollback lists `frozen_config_not_restored` / `link_inputs_not_restored`: show them to the operator. A frozen child whose read-back failed carries `readback_error` and makes the verdict `unverified`, not `partial`: report it as "could not check", never as "missing".
- Never ask for or suggest a tier opt-in to get past a refused write without the PoC or probe that tier requires; the opt-in is the operator's record that it ran.
- Never invent a bare "cannot": give the route ladder from METHODOLOGY section 1 (cost, needs, next step).
- Live diagnosis of a restart: take the timing from the station log, not from oBIX `about/serverBootTime` (oBIX said 00:19:30; the station log showed the restart at 00:06:45-00:08:42); use oBIX only as a cross-check. `[ev: external retro niagara-research/retros/2026-10-06-panccadia-comppan-hmi-support.md Δ6]`
- A confirmation token belongs to the MCP server session: after "Could not find Server Session" and a new `n4_connect`, every pending token is dead. Redo the dry runs; never resend the old token. `[ev: external retro niagara-research client A 2026-11-10]`
- `n4_remove_component` refuses at the dry run when its scan (the write-scope prefix holding the parent, or the narrower `link_scan_ord`) finds links from the subtree into other components: show the operator the listed links and pass `acknowledge_links: true` only after they agree to break them. `[ev: retro 2026-11-15-lab-415-bench-session-2 Δ3]`
- Before re-pointing links into a facade slot, `n4_list_links` the target (depth 1) and remove or roll back the old links first; a slot fed by two links silently shows whichever wrote last. `[ev: external retro niagara-research client A 2026-11-10]`
- Modbus client points: `n4_set_slot` writes the device `deviceAddress` (`baja:Integer`), the point's `proxyExt/dataAddress/addressFormat` (`baja:Simple` `modbus`) and `proxyExt/dataAddress/address` (`baja:Simple` with the number, e.g. `40005`; the client turns a numeric string into a number), `proxyExt/dataType` (`baja:Simple` tag, e.g. `signedInteger`) and the scaling `proxyExt/conversion` (`baja:Simple`, `simple_type` `driver:LinearConversion`, value `0.1;0.0`). After a field fix, `n4_invoke_action` `ping` on the device re-checks it. For N identical devices, configure one, then `n4_copy_component` it (up to 30 per batch) and set each copy's `deviceAddress`; the copy leaves out runtime slots by flags (frozen slots declared readonly, transient or default-on-clone; dynamic slots flagged transient or remove-on-clone; all listed in the plan notes) and links, and keeps the flags an integrator set. `[ev: retro 2026-11-12-jace-modbus-dashboard-audit Δ1 Δ2]`
- History extensions: use `n4_add_history` (one dry run and one token for up to 50 points, created already configured and enabled; the extension type and default name follow the point type, and a history id that would repeat on the station is refused at the dry run; `mode=cov` makes change-of-value extensions, without `interval_ms`; `capacity` sets the records kept, or `"unlimited"`, in the same batch: a dashboard with 7 d / 30 d views needs it, the default 500 records is about 41.7 h at 5 min). By hand, the recipe is `n4_create_component` `history:NumericIntervalHistoryExt` under the point (it is created DISABLED, `BHistoryExt.enabled` default false), then `n4_set_slot` `historyName` (`baja:Format`, unique per device: the default `%parent.name%` collides across devices with equal point names, e.g. `S%parent.parent.parent.name%_%parent.name%`), `interval` (`baja:RelTime`, ms; the top-level ext slot, not `historyConfig/interval`), and last `enabled=true`. `[ev: external retro niagara-research client A 2026-11-10]`
- Slot flags: `n4_set_flags(ord, slot, flags)` replaces the complete flag set of one slot (letters such as `h` hidden, `o` operator, `r` readonly, `s` summary; `""` clears them); to change some letters and keep the rest, pass `add` and/or `remove` instead of `flags` (`add: "s"` keeps an existing `r`). The dry-run note shows the current and the resulting set. A frozen slot at its declared flags shows none in a read, so the current set comes from its type contract. The station applies it only for a user with admin write on the component, and a restricted user is shown `h`/`r` the slot does not hold. `n4_rollback` restores the previous set. Live on 4.15.6.20 for a dynamic slot, a frozen property and a frozen action. `[ev: retro 2026-11-14-lab-415-bench-session Δ9]`
- Never contact a station the operator did not configure and authorize.
- If the harness permission classifier blocks a live write, surface it to the operator and stop; never route around it (no other tool, subagent or peer session).
- Close with the session retro (`n4_session_retro_draft` / `retro-draft --write`): proposed kit deltas, never applied unprompted; never stage issues automatically.

## Output Contract

Report: kit path, station name and tier, each write as `requested / observed / verdict` with its `batch_id`, dangling-output result, save evidence, and the retro line.
