Thin launcher. The real content lives in an EXTERNAL kit (METHODOLOGY, README, server code) — read it, don't restate it from memory.

## Resolve the kit (do this first)

`KIT` = the `mcp-n4-kit` directory: it holds `METHODOLOGY.md` and `README.md`; the server it launches is the Go binary `$KIT/../go/bin/mcp-n4` (the only server since S17). Resolve once:
1. `$MCP_N4_KIT` if set and it contains `METHODOLOGY.md`.
2. Else the default: `/home/cristian/modulos_niagara_n4/niagara-tools/mcp-n4-kit`, the author's checkout on the primary machine (confirm `METHODOLOGY.md` exists). The installed launcher is a copy in the agent harness's skills directory (`<harness-dir>/skills/mcp-n4/`), so its own location says nothing about the kit; on any other machine or checkout set `MCP_N4_KIT` to the `mcp-n4-kit` directory.
3. Else STOP searching and say so plainly: "the mcp-n4 kit is not on disk at <path checked>". A checkout on another branch may lack `mcp-n4-kit/`; never switch a shared checkout's branch to get it. Offer the operator one of:
   - a worktree of `origin/main`: `git -C <niagara-tools checkout> fetch origin && git -C <niagara-tools checkout> worktree add <path> origin/main`, then `MCP_N4_KIT=<path>/mcp-n4-kit`;
   - an installed copy they already have (set `MCP_N4_KIT` to it).
   Ask before creating the worktree.

Then read `$KIT/METHODOLOGY.md` FIRST and follow its session checklist.

## Register the server

Follow `$KIT/README.md` ("Running the server", "Getting the kit and registering it per project"). Register the server once in the MCP configuration of the harness you run in (Claude Code: the project's `.mcp.json`; pi and pi-based harnesses: `<agent-dir>/mcp.json`, where the tools are named `mcp__mcp_n4_<station>__<tool>`: hyphens become underscores; README "Registering the server per harness") rather than driving stdio by hand. Launch the Go server `$KIT/../go/bin/mcp-n4` (absolute path; build it with `cd $KIT/../go && go build -o bin/ ./cmd/mcp-n4` if it is missing). The operator, not the model, chooses stations, credential env prefix, TLS policy and timing (`--station NAME=https://…`, `--credential-env`, `--insecure-tls NAME`, `--load-wait`, `--http-timeout`, `--auth-cooldown`), and where each station keeps its `config.bog` (`--station-home NAME=PATH`, so `n4_save_station` can prove persistence). Writes need `--allow-writes` plus at least one `--write-scope`; the default is read-only. A tier B or C station (METHODOLOGY section 5) also needs the operator's `--allow-tier-b NAME` / `--allow-tier-c NAME`, given only after the PoC or probe that tier requires. If no station is configured, stop and tell the operator which flag is missing.

## Before acting on an operator's hand edit

Before step 5 (and before relying on anything the operator wrote by hand or says is done, e.g. "ya lo hice"), read the value back live (`n4_read_slots`) and compare it with the intended value; never trust the confirmation alone. Evidence: `hmiPanelAddress` typed as 192.168.1.140 instead of .40, caught only by a live read-back. `[ev: external retro niagara-research/retros/2026-10-06-panccadia-comppan-hmi-support.md Δ3]`

## Session checklist (full detail in METHODOLOGY section 4)

1. `n4_describe_session`, `n4_connect` to a configured station; confirm the real station name, `version` and `tier` (when the operator names the version, pass `expected_version` so a mismatch refuses the session). A stale-binary `warning` in `n4_connect` or `n4_describe_session` means the server binary on disk is another build than the one serving: tools added since are missing until the operator restarts the MCP server (`server.build` names the revision that serves). After rebuilding the mcp-n4 binary, restart the MCP server (the client keeps the old process); `n4_describe_session`'s stale-binary warning shows it; never conclude a tool is missing before checking `server.build`. With `tier_writes: refused`, plan with dry runs only (they carry `tier_gate`) and give the operator the refusal's routes.
2. "How is the station?" (state, CPU and memory, how many points and how many are down or stale, drivers, licence capacity): `n4_station_health` FIRST, one call; then drill into what it names (`not_ok` paths with `n4_read_slots`, a network with `n4_inventory`). "Which drivers are unhealthy?": the same call with `drivers: true` adds per network the field devices down/fault/disabled and the proxy points stale/fault/down/disabled, the bad ones listed (`max_bad`), from the same rows: no extra request. "Why are these devices down?": add `device_detail: true` (with `drivers: true`) for each bad device's `fault_cause`, `last_fail_cause`, `last_ok`, `address`, `stale_points` and each network's `port` and `pattern` (`bus`: wiring, termination, polarity, or the network path on IP; `single`: that device's address and power). "Is the platform near a limit or about to expire?": `platform: true` adds heap, history records, licence and trust store certificate expiries and module count, with `warnings` (`expiry_warn_days`, default 30). Read each section on its own: one with `error` failed while the others answered; `truncated` cut the `not_ok` list only (`not_ok_count` is whole), `rows_truncated` makes the counts lower bounds; a status whose only flag is `null` (a point with no value, e.g. an unlinked input) is not a fault: it is counted in `null_only` and never listed in `not_ok`, and `ok + null_only + not_ok_count = total`; `null` beside another flag is not ok. `capacity: null` means the capacity could not be read (see `capacity_note`: the user may not read spy pages, or the page has no Global Capacity table on this version), NOT zero usage and NOT "no limit": say it is unknown and offer the Workbench Resource Manager view; `unlimited: true` is the station showing no limit for that resource. Two counts sit side by side in `capacity.resources`: `used` is the licence's own tally, the number to quote against `limit` for licensing ("points consumed"), and `live` is what the station really holds now (networks, devices, and `points.proxy`: a licence counts proxy points, not every control point in `points.total`). The tally only grows until a capacity recount or a station restart, so with `may_be_inflated: true` say that `used` may overstate and give `live` beside it; `capacity_truncated: true` means resources may be missing from the list. `license` is the licence in short: `licenses` with `valid` and `days_left` (from the station's date), `nearest_expiry`, `expired` and a `warning` when the nearest expiry is 60 days away or fewer, a licence is not reported valid, or an expiry could not be read; report a `warning` to the operator unprompted, and treat `license.error` as "the licence was not read", never as "no licence"; `n4_license_info` has the detail (certificates, features, SMA facts). Inventory or wide reads: `n4_inventory` / `n4_bql_query` FIRST (METHODOLOGY section 7); `n4_navigate` (declared properties still at their default are listed too under each component or struct slot listed, marked `default: true`; `value: null` with a note when the contract gives no default; the sub-entries of a declared struct default are marked `default: true` too and may show `type: null`; `defaults_note` names what could not be read or decoded; optional `types` filter, which also keeps subtypes: `history:HistoryExt` finds every history extension) / `n4_read_slots` only for targeted components. History records: `n4_read_history` (a `history_id` such as `/MyStation/MyPoint`, or the extension's `ext_ord`) returns the last records newest first with `total_records`; "how high did it get?" is ONE call: `summary: true` (with `start: "24h"` or a BAbsTime range) adds `summary` {count, min and max with their ISO timestamps, first, last, status_counts} over the WHOLE range whatever `limit` cut (records with status `null` (no value) or a `nan`/`inf` value are counted but left out of min, max, first and last: `excluded_from_extremes` counts them and `first_record`/`last_record` keep the raw ends) (`complete: false` with a note when the range exceeds `summary_max_rows`; then `range_min`/`range_max` are the station's whole-range aggregate); use it to prove a history collects (an extension status `{ok}` proves it runs, not that records exist), and when it names a history it cannot read, list the ids with `n4_bql_query` `select historyConfig.id from history:HistoryExt`. A free select over the alarm database or one history is `n4_bql_query` with `base` `alarm:` or `history:/<station>/<history name>` and `select <cols> [where ...] [order by ...]` (no `from` clause; e.g. `where timestamp.millis >= <epoch ms>` for a time range): same rows as a station base, read-only. Alarms: `n4_read_alarms` (open alarms by default, newest first; filters `source`, `source_glob` (a like pattern such as `*slot:/Drivers/Net/D*`), `alarm_class`, `source_state`, `ack_state`, `since`/`until` (BAbsTime or `30m`/`24h`/`7d`); `total` counts the matches and `state_counts: true` counts them per source and ack state; a `$xx` escape that BQL decodes to a quote, space, `*` or `|` is refused; each row adds `timestamp_iso`, `normal_time`, `ack_time` in ISO-8601) and `n4_list_alarm_classes` (priorities and `ack_required` per transition, counts, and the recipients each class is linked to through its `alarm` topic); before or after writing alarm texts run `n4_alarm_text_check` (LC9: `parent-path`, `empty-tonormal`; read-only); a new class is the README recipe (`n4_create_component` `alarm:AlarmClass`, `n4_set_slot` `priority`/`ackRequired`, `n4_create_link` `alarm` to the recipient's `routeAlarm`). Acknowledge with `n4_ack_alarm` (`uuids` from `n4_read_alarms`, or `select: {source?, alarm_class?, before?, max?}` resolved to exact uuids in the dry run's `plan.selection`, the token bound to that list; it cannot be undone, so show the operator the records first). Px graphics are files: `n4_list_px_views`, then `n4_px_summary` / `n4_read_file` on the `px_file` (METHODOLOGY section 9). Diagnostics are spy pages: `n4_spy_page` (empty `path` for the index, then a `links[].path`) returns a page's tables as data (a type's registry page is `sysManagers/registryManager/types/<module>:<Type>`: supertype and interfaces, not its slot defaults; the `sysManagers/registryManager/types` page links to each type page); it only reads (the `actions` a page lists are never invoked), needs a station user allowed to read spy pages (`status: forbidden` otherwise), and its tables are the station's own layout, which differs between Niagara versions: read them as found, never by a fixed row position. "Which licence, until when, certificates, SMA?": `n4_license_info`, one call (host id, certificates, licences with `days_left`, brand, owner, project, `nearest_expiry`, `expired`, the feature list; `feature` narrows it). "Will N more devices or points fit the licence?": the same call with `plan: {add_devices, add_points}`; read `usage` (used vs `device.limit`/`point.limit`, excluded modules left out) and `plan_result.fits` (`null` = unknown, never "fits"); `n4_create_component` refuses in its dry run a device that would exceed `device.limit`. Its `days_left` counts from the STATION's date (`station_date`), never this machine's; `null` means unknown or `never`, not zero. A licence or certificate with `valid: false` carries `state` (the page's own word): report it as not valid, whatever its date. An `expires` that is neither `never` nor a date comes back as written with `days_left: null` and is counted in `note`: say the expiry could not be read, never that it does not expire. A string ending in `...[cut]`, `attributes_truncated`, `sma_truncated` or a `*_count` above the list length mean the reply was bounded: read the page with `n4_spy_page` for the rest. `maintenance` reports only what the licence states: `sma_attributes` (per feature, its `sma.*` attributes), `sma_exempt_features` (the features with `sma.exempt=true`: each exempts that one feature only, so never say "the licence is SMA exempt") and a maintenance feature if any; its `expires` is `null` unless a local licence file states a `maintenanceExpiration`, because the page has no SMA end date: never present a licence expiry as the SMA end date, say the licence does not state it. When a licence was generated (`generated`), its `version` and that SMA date exist only in the licence files of the installation, so they appear only when the server was started with `--niagara-home NAME=PATH` for that station (an installation reachable from this machine); otherwise they are omitted and `generated_note` says why: tell the operator they are not available remotely instead of guessing a purchase date. A `status` other than `ok` (`forbidden`: the user may not read spy pages) means the licence was NOT read, not that there is none. Tags: `n4_read_tags` (up to 50 ORDs) gives the direct tags, tag groups, relations and the implied tags the dictionaries compute; `implied: null` with `implied_unavailable` means they were not read, never that there are none. `n4_neql_query` finds components by tag (one NEQL GET below base_ord; optional bql select on the matches); `n4_list_tag_dictionaries` lists what the installed dictionaries define (tags, value types, groups, relations). "Which points are untagged, which equips have no points, which tags are not in a dictionary?": `n4_tag_coverage`, one call; feed its point ORDs to `n4_set_tags`. A read or client expected to exceed ~1 min writes progress to a file and reports counts; never rely on stdout piped through `tail`.
   - "Export these histories for a client report": `n4_export_history` (`history_ids` 1-20, a range), one CSV under `<state-dir>/exports/`; give the operator the returned `path` and check `per_history[].truncated`.
   - "Which COV tolerance should this history use?": `n4_read_history` with `cov_hint: true` (and a range); report `suggested_tolerance` with its `rule` and `reduction_estimate`; it is a suggestion only, write it with `n4_set_slot` only if the operator asks.
   - "How high did it get during that alarm?" (peak and when, alarm/normal/ack times): `n4_event_report` on the alarm source, one call, never n4_read_alarms then n4_read_history by hand.
   - "What is this station running?" or "does it need a restart after the deploy?": `n4_station_runtime`, one call (uptime, loaded modules with versions and, when the server has `--niagara-home` for the station, the jars on disk with `mismatches`). `restart_needed: null` means unknown (`restart_note` says what is missing, e.g. no `--niagara-home`), never "no restart needed".
3. Write tools with `dry_run=true` (the default); show the plan to the human.
4. After approval, repeat with `dry_run=false` and the `confirmation_token`. The token is bound to the plan including its warnings (a create's "name is already taken" note): a re-used create token, or a name taken after the dry run, is refused as a plan mismatch; redo the dry run. A remove's token leaves out the values of transient slots (marked `"runtime": true` in the plan, such as an alarm extension's `timeInCurrentState`), so their ticking never stales it; a child added, a configured value changed or an alarm transition (persisted `alarmState`) still does.
Tags are written with `n4_set_tags` only (never `n4_set_slot` or `n4_create_component` with an escaped name): check the definitions first with `n4_list_tag_dictionaries`; an undefined tag needs `allow_ad_hoc` and a namespace of its own, never an installed one (`n:`, `hs:`, `h4:`). Tag groups and relations go through its `add_groups`/`remove_groups` and `add_relations`/`remove_relations`.
5. Read the verdict; `n4_find_dangling_outputs`; `n4_save_station` with persistence evidence.
   - Finishing a job ("what is still wrong or unfinished here?"): `n4_commissioning_report` on the job's folder or network (`scope`), one call, before the save; say which points should be trended and alarmed with `expect_histories` / `expect_alarms` (`{"kinds": ["numeric"], "name_pattern": "*Temp*"}`, `{}` for every point; without `expect_histories` the points with no history are only counted, without `expect_alarms` a missing alarm extension is not a finding). Read `summary` first, then each section's `checks`: `{count, items, more}` ran (`more` above zero: raise `limit` or narrow `scope`), `{not_checked: why}` did NOT run (a failed or impossible read: report it as "not checked", never as clean), `{skipped: why}` was not asked for. `state: partial` is "clean in what ran, something did not run", not ok. `unsaved_changes` and `last_backup` are always not checked (the station does not expose them): check them by hand. With `truncated: true` the counts are lower bounds: narrow the scope. The `station` section runs only with the whole station as scope. After a Spyder Full Download, never call it done from the job dialog alone: run it with `sections: ["spyder"]` on the BACnet network (`deviceStatus=1`, `compileStatusFlag=0`, `sErrorStatus` empty, `enabled` true; a Spyder left `Enabled=false` is listed under `disabled`), and pass `spyder_spec` (`{"2005": {"RA_T": {"sensor_type": 0, "terminal": 1}}}`) to compare each IOComp with the job's IO table instead of reading them by hand. README "Finishing a job" has the checks and the recipe.
6. Keep every `batch_id` (`n4_list_batches` lists them, newest first).
7. Close with the session retro: call `n4_session_retro_draft` (or run `$KIT/../go/bin/retro-draft --write --station NAME --state-dir DIR`), review the candidate deltas, keep or edit them (or leave the honesty line `no new deltas`). Propose, never apply; stage issues only by hand.

## Hard Rules (non-negotiable)

- Never write without showing the dry-run plan to the human first.
- No credentials in tool arguments or chat; they come from the operator's environment.
- Never retry a failed login: 5 failures in 30 s lock the account. On a 401, have the operator check the user's Authentication Scheme Name = `HTTPBasicScheme`, then the password.
- Report `partial`, `mismatch`, `failed`, `unverified`, `in-doubt` and `persisted: unknown` exactly as returned; never call them success. A `partial` rollback lists `frozen_config_not_restored` / `link_inputs_not_restored`: show them to the operator. A frozen child whose read-back failed carries `readback_error` and makes the verdict `unverified`, not `partial`: report it as "could not check", never as "missing".
- Never ask for or suggest a tier opt-in to get past a refused write without the PoC or probe that tier requires; the opt-in is the operator's record that it ran.
- Never invent a bare "cannot": give the route ladder from METHODOLOGY section 1 (cost, needs, next step).
- Live diagnosis of a restart: take the timing from the station log, not from oBIX `about/serverBootTime` (oBIX said 00:19:30; the station log showed the restart at 00:06:45-00:08:42); use oBIX only as a cross-check. `[ev: external retro niagara-research/retros/2026-10-06-panccadia-comppan-hmi-support.md Δ6]`
- A confirmation token belongs to the MCP server session: after "Could not find Server Session" and a new `n4_connect`, every pending token is dead. Redo the dry runs; never resend the old token. `[ev: external retro niagara-research client A 2026-11-10]`
- `n4_remove_component` refuses at the dry run when its scan (the write-scope prefix holding the parent, or the narrower `link_scan_ord`) finds links from the subtree into other components: show the operator the listed links and pass `acknowledge_links: true` only after they agree to break them. `[ev: retro 2026-11-15-lab-415-bench-session-2 Δ3]`
- Before re-pointing links into a facade slot, `n4_list_links` the target (depth 1) and remove or roll back the old links first; a slot fed by two links silently shows whichever wrote last. `[ev: external retro niagara-research client A 2026-11-10]`
- Modbus client points: `n4_set_slot` writes the device `deviceAddress` (`baja:Integer`), the point's `proxyExt/dataAddress/addressFormat` (`baja:Simple` `modbus`) and `proxyExt/dataAddress/address` (`baja:Simple` with the number, e.g. `40005`; the client turns a numeric string into a number), `proxyExt/dataType` (`baja:Simple` tag, e.g. `signedInteger`) and the scaling `proxyExt/conversion` (`baja:Simple`, `simple_type` `driver:LinearConversion`, value `0.1;0.0`). After a field fix, `n4_invoke_action` `ping` on the device re-checks it. For N identical devices, configure one, then `n4_copy_component` it (up to 30 per batch) and set each copy's `deviceAddress`; to add the same M points to N existing devices, `n4_replicate_points` does N x M adds under one token (per-target `copies[]` name/address overrides; one budget write per add, refused up front when over `write_budget.remaining`) `[ev: niagara-tools n4_replicate_points, retro U10]`; the copy leaves out runtime slots by flags (frozen slots declared readonly, transient or default-on-clone; dynamic slots flagged transient or remove-on-clone; all listed in the plan notes) and links, and keeps the flags an integrator set. `[ev: retro 2026-11-12-jace-modbus-dashboard-audit Δ1 Δ2]`
- History extensions: use `n4_add_history` (one dry run and one token for up to 50 points, created already configured and enabled; the extension type and default name follow the point type, and a history id that would repeat on the station is refused at the dry run; `mode=cov` makes change-of-value extensions, without `interval_ms`; `capacity` sets the records kept, or `"unlimited"`, in the same batch: a dashboard with 7 d / 30 d views needs it, the default 500 records is about 41.7 h at 5 min; `full_policy` `roll` (default) or `stop`; `change_tolerance` sets the numeric COV dead band, numeric points only: N points with the same settings are ONE call, never one per point or a `n4_set_slot` per slot). By hand, the recipe is `n4_create_component` `history:NumericIntervalHistoryExt` under the point (it is created DISABLED, `BHistoryExt.enabled` default false), then `n4_set_slot` `historyName` (`baja:Format`, unique per device: the default `%parent.name%` collides across devices with equal point names, e.g. `S%parent.parent.parent.name%_%parent.name%`), `interval` (`baja:RelTime`, ms; the top-level ext slot, not `historyConfig/interval`), and last `enabled=true`. `[ev: external retro niagara-research client A 2026-11-10]`
- Renaming a component: until mcp-n4 has a rename tool, renaming is a Workbench step (right click → Rename). Never rename by creating a new component and removing the old one: the old one's history extension, its history id and every link into it are lost. Give the operator the list of slots to rename instead. `[ev: external retro niagara-research client B 2026-11-16 U2]`
- Many links at once: `n4_create_link` with `links` (1 to 50 `{source_ord, source_slot, target_ord, target_slot}`) under one dry run and one token, one budget write per link; check `verdict` (`partial` names the missing ones per entry in `observed`) and undo the whole batch with `n4_rollback`. `[ev: niagara-tools field retro delta U11]`
- Repeated equipment from a template: `n4_deploy_template` deploys a local `.ntpl` under a parent with its settings (dry run lists the tree, the resolved settings and every dropped item: the template's own `templateConfig`, links and ORD values are not deployed, so recreate needed links with `n4_create_link`). Station and application templates are refused. `[ev: niagara-tools #757]`
- Copy/replicate fallback: a dry-run note on a writable point with a non-null `fallback` means every copy commands its device with that value on first communication; confirm it is safe or null it on the copies before executing. `[ev: retro U18]`
- Write budget: `--max-writes` counts executed writes per server process; `n4_save_station` is outside it, and every write reply carries `write_budget.remaining`. Plan a bulk job against `remaining` and save before it runs out of other writes. `[ev: niagara-tools #750]`
- Alarm extensions: use `n4_add_alarm` (one dry run and one token for up to 50 points): the kind follows the point type (numeric `out_of_range`, boolean `boolean_change_of_state`, enum `enum_change_of_state`, string `string_change_of_value`; `status` fits any point), `alarm_class` must exist (the refusal lists the classes), a limit given is also enabled (`limitEnable` defaults both off), `alarm_enable` is a list of `offnormal`/`fault`/`normal`/`alert`, and the texts are `baja:Format` resolved against the alarm record: `%alarmData.sourceName% high: %alarmData.presentValue% > %alarmData.highLimit%`, never `%parent...%` (that works only in `source_name`). A second extension of the same kind is refused unless `allow_second=true`; the read-back lists any value the station stored differently under `coerced`. Recipe and encodings: README "Alarm extension recipe". `[ev: bench retro 2026-11-15 row 10]`
- Slot flags: `n4_set_flags(ord, slot, flags)` replaces the complete flag set of one slot (letters such as `h` hidden, `o` operator, `r` readonly, `s` summary; `""` clears them); to change some letters and keep the rest, pass `add` and/or `remove` instead of `flags` (`add: "s"` keeps an existing `r`). The dry-run note shows the current and the resulting set. A frozen slot at its declared flags shows none in a read, so the current set comes from its type contract. The station applies it only for a user with admin write on the component, and a restricted user is shown `h`/`r` the slot does not hold. `n4_rollback` restores the previous set. Live on 4.15.6.20 for a dynamic slot, a frozen property and a frozen action. `[ev: retro 2026-11-14-lab-415-bench-session Δ9]`
- Schedules: `n4_read_schedule` first (kind, weekly ranges, special events, dates, `out`), then `n4_set_schedule`: `weekly` replaces only the days given (`{"sunday": []}` clears one), plus `default_output`, `add_special_event` / `remove_special_event` (the order is the priority; a date that already ended is refused unless `allow_expired`), `add_date` / `remove_date` on a calendar or trigger and `times` on a trigger; every fault is named before anything is sent. A schedule drives a point through a link from its `out` to the point's `in16` (README "Recipe: a schedule that drives a point").
- "Which accounts are admins, disabled, expired, locked or unused?": `n4_users_audit` (unused_days 90), one call; it never returns a credential, hash or contact value (only `masked_slots` names them), and `last_login` comes from the SecurityHistory `Login` records, null with a note when they cannot be read.
- "Which Px graphics show a broken binding?": `n4_px_binding_audit` (every view below `root`, or one `file_ord` with `base`), one call; `broken` holds only proven misses, `unknown` carries a `why` and is never reported as broken.
- "Which schedules drive nothing, which have no next event, what holidays come this week?": `n4_schedule_audit` (base, `horizon` 7d), one call; `unlinked`, `no_next_event` and each schedule's `special_events.upcoming`; a null value carries a note, never a guess.
- "What changed in this subtree since then?": `n4_inventory_snapshot` (base, depth) before and after, then `n4_inventory_diff(a, b)` on the two names; runtime state (transient slots per the type contract, computed outs, linked inputs) is left out; a `fallback` change is reported, so an unchanged station diffs to empty.
- Never contact a station the operator did not configure and authorize.
- If the harness permission classifier blocks a live write, surface it to the operator and stop; never route around it (no other tool, subagent or peer session).
