# Type: station service — a `BAbstractService` other code finds by type

A service is a component the station registers under one or more types, so any code in the station reaches the one
instance with `Sys.getService(Type)` instead of an ORD. Author one for a station-wide singleton (a manager, a
gateway, a shared connection); a thing that exists per room or per device and is reached by slot path stays a plain
`BComponent`. `[ev: corpus B757 §757.2]`

Related cards: the other author-side SPIs (ORD scheme, subscription, job) are in `types/logic-authoring.md`
§ Author-side SPIs; licensing a service is `types/security.md` § 5; a driver network is a service-like component
with its own card, `types/driver-authoring.md`.

Sources: corpus B757, B778 (authoring), B1145 (start and stop sequence), B1143 (licence enforcement), B1416 and
B1419 (course recordings checked against code), B20 (overview). Code read for this card:
`ServiceManager`, `Station` and `ComponentSlotMap` of the 4.14.0.162 `baja` decompile (`organized/baja/baja/vineflower/com/tridium/sys/`,
under niagara-research); the 4.15 classes were not diffed.

## 1 · Minimal skeleton

```java
@NiagaraType
public final class BFooService extends BAbstractService {
  // TYPE and getType() generated by Slot-o-Matic

  @Override
  public Type[] getServiceTypes() { return new Type[] { TYPE }; }   // never an empty array

  @Override
  public void serviceStarted() throws Exception {
    // other services are registered; ordinary components have NOT started yet
  }

  @Override
  public void serviceStopped() throws Exception {
    // release what serviceStarted() acquired
  }
}
```

- `BAbstractService` is a `BComponent` that implements `BIService`, `BIStatus` and `BILicensed` and brings three
  frozen slots: `status`, `faultCause`, `enabled`. `[ev: corpus B757 §757.1]`
- **`getServiceTypes()` is mandatory and must return the service's own type.** It is abstract; an IDE-generated body
  returns an empty array, and then the service registers under nothing and no lookup ever finds it. A type the
  service is not an instance of is rejected with a SEVERE `not instanceof` log line. Return a base type or an
  interface type as well when callers should find the service by that abstraction. `[ev: corpus B1419 §1419.1]`
- Verify-gate read: every service class has a `getServiceTypes` that returns a non-empty array containing `TYPE`.

## 2 · Where it lives and how it registers

- **Registration is by placement, not by annotation or by installing the jar.** A `BIService` registers when it is
  mounted in the station's component space, under each type it returns; it unregisters when unmounted. Nothing
  appears in a station until someone adds the component. `[ev: corpus B757 §757.1]` `[ev: corpus B778 §778.1]`
- **Convention: directly under the station's frozen `Services` container.** The registration code accepts a service
  mounted anywhere in the station space [CERT] (`ServiceManager.register` checks only the component space), but
  integrators, the framework's own services and the documentation all expect `Services`. Ship the service in the
  module palette so commissioning is one drag (palette authoring: corpus B746).
- **Enforce the placement and the singleton** by implementing `BIRestrictedComponent`
  (`types/logic-authoring.md` § BIRestrictedComponent — placement constraint): a second instance of a restricted
  service is logged SEVERE (`Unable to start duplicate restricted service … This service will be removed`) and removed
  from its parent at start. `[ev: corpus B757 §757.2]`
- **Nav tree:** a service appears in the Workbench nav like any component, with no extra code.
  `[ev: corpus B757 §757.3]`

## 3 · How others find it

- `Sys.getService(BFooService.TYPE)` returns the **first-registered** instance and throws `ServiceNotFoundException`
  when none is registered; `Sys.getServices(Type)` returns all. A duplicate is not rejected at registration: without
  `BIRestrictedComponent`, a second instance is silently never returned by `getService`. `[ev: corpus B757 §757.2]`
- **A caller must survive the service being absent.** The station may not have it (never added, removed, module not
  installed): catch `ServiceNotFoundException`, surface a config fault on the caller, and look it up again later;
  never cache the reference past the caller's `stopped()` `[INFER]`.
- A configurable pointer instead of a hard-coded type: the `service:` ORD scheme
  (`types/logic-authoring.md` § `service:` lookup scheme).
- Lookups, links and subscriptions do not care which module the service came from
  (`types/logic-authoring.md`, "Within a station, runtime comms is module-AGNOSTIC").

## 4 · Lifecycle callbacks and their order

**Station start** [CERT] (`Station` boot sequence; `[ev: corpus B1145 §1145.1]` `[ev: corpus B20 §20.3.2]`):

| # | Phase | What runs on your service |
|---|---|---|
| 1 | load `config.bog`, mount the tree | the service **registers** (lookups by type now find it; it has not started) |
| 2 | services initialize | licence check (§ 5), then **`serviceStarted()`**, service by service |
| 3 | station start | **`started()`** on every component of the tree, the service included, then `descendantsStarted()` |
| 4 | station started | `stationStarted()`, once per station boot |
| 5 | steady state | `atSteadyState()` |

- **In `serviceStarted()` other services are registered but not necessarily started, and no ordinary component has
  started.** Resolve peers with `Sys.getService` there; do not read point values or expect links to have propagated.
  Work that needs the running tree goes in `started()` or `atSteadyState()` (`types/logic.md` § Safety fail-modes &
  timers for arming timers). `[ev: corpus B778 §778.1]` `[ev: corpus B20 §20.3.1]` Do not depend on the order in which
  sibling services start `[INFER]` (the component rule, corpus B1416 §1416.1).
- **A throw out of `serviceStarted()` does not stop the boot.** It is logged SEVERE `Service start failed: <service>`
  and the next service starts; your service is left registered and half-initialized. Catch inside, and report with
  `configFail(cause)` so the fault is visible on the `status` slot. `[ev: corpus B1145 §1145.2]`
- **Dropped into a running station** (a palette drag), a service registers and
  `serviceStarted()` runs at once, then `started()` as for any added component; `stationStarted()` does **not** run
  again, so startup logic placed there is skipped. [CERT] `ServiceManager.register` starts a service when services
  are already running; `[ev: corpus B1416 §1416.3]`
- **Enable / disable is not start / stop.** Setting `enabled` false calls `disabled()`, true calls `enabled()`;
  `stopped()` does not fire. Gate work on `isOperational()` (not fatal-faulted, not disabled, not in fault), and
  release in `disabled()` what must not run while disabled. `[ev: corpus B1416 §1416.2]`
- **Removed from a running station:** `serviceStopped()` runs, then the service unregisters. [CERT]
  `ServiceManager.unregister`.
- **Station stop** [CERT] (`Station.shutdown`): the station is saved, then the component tree stops (`stopped()` on
  every component, your service included), and only then the services stop (`serviceStopped()`). So in
  `serviceStopped()` the components that used the service have already stopped; in a component's `stopped()` the
  services are still registered. A console `kill`, a process kill or a power loss runs none of this
  (`types/diagnostics.md` § 4.1): persist what must survive as it changes, not in `serviceStopped()`.
- **Fault states:** `configFail(cause)` sets a recoverable fault that `configOk()` clears; `configFatal(cause)` and an
  unlicensed feature set a **fatal** fault that only a restart of the service clears. `status` and `faultCause` are
  read-only and cannot be edited to hide a fault. `[ev: corpus B1143 §1143.3, §1143.6]`
- The asynchronous hooks `completesStarted()` / `whenServiceStarted()` (a service that finishes starting later) are
  named in the code and not exercised by us: open (niagara-research B757-G1).

Symmetry rule, as for any component: whatever `serviceStarted()` or `started()` acquires (threads, sockets,
subscriptions, tickets), `serviceStopped()` or `stopped()` releases
(`types/logic-authoring.md` § Subscribe / unsubscribe symmetry rule).

## 5 · Licence behaviour

Covered once in `types/security.md` § 5 and § 5.1; what a service author must keep in mind here:

- A service is unlicensed-by-design unless it overrides `getLicenseFeature()`.
- With a feature, the framework checks it **once, at service start, before `serviceStarted()`**; a failure sets a
  fatal fault with cause `Unlicensed: …` and a SEVERE log line, and then `serviceStarted()` runs anyway. The fault is
  advisory: only your own `isOperational()` gates stop the work. `[ev: corpus B1145 §1145.1]`
  `[ev: corpus B1143 §1143.2]`
- A per-use limit (`<name>.limit` properties of the feature) is counted per JVM across every instance of the feature,
  an absent limit is unlimited, and the counter is not checked at all when the feature check failed: one more reason
  for the `isOperational()` gate. `[ev: corpus B1143 §1143.4-1143.5]`

## 6 · Testing

- A service needs a station: use a `BTestNgStation` test (`types/moduleTest.md` § TEST-G1), add the service under
  `Services` in the test station's configuration, and assert through the public surface.
- What to pin, one test each:
  1. **Registered and started:** `Sys.getService(BFooService.TYPE)` returns the instance and an observable effect of
     `serviceStarted()` is present.
  2. **Absent:** a caller of the service, in a station without it, reports a fault and does not throw.
  3. **Disabled:** set `enabled` false; the work stops and `status` shows disabled; set it true; the work resumes
     without a second set of timers or subscriptions.
  4. **Removed and re-added on a running station:** remove the component, then add a new one: no leaked thread or
     ticket, and the lookup returns the new instance.
  5. **Unlicensed**, when the service has a feature: `types/security.md` § 5.
- The test station is built once per test class, not per method: make fixtures idempotent
  (`types/moduleTest.md`, the `BTestNgStation` bullet under "Client parity doctrine").
- Worked exemplars: the course certification exam's export service and the Review Assignment's summary service,
  corpus B1354 and B1254; a shipped restricted service, `BSystemMonitorService` `[ev: corpus B778 §778.1]`.
