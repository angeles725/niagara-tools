## What happened
Comparing the course's authoring files with the kit's how-to found four places where the kit is thin or wrong. (1) The
kit's library guide leads with the Shadow plugin (`types/third-party-libraries.md:38-80`) and mentions the plugin's
built-in `uberjar(...)` only in one table row (`types/module-wiring.md:17`); Tridium teaches `uberjar(...)` (Lab 6,
Jackson) and `testUberjar(...)` (Lab 7, Mockito) and has no table of which `java.*` APIs need which permission group.
(2) The kit's palette example (`types/structure.md:150-165`) writes the type as a Java class name
(`t="com.angeles.coldroomrt.BColdRoomPan"`) and slot overrides as XML attributes (`hasDefrost="true"`); every Tridium
palette uses a module prefix (`m="k=kitControl" t="k:Nor"`) and child `<p n="<slot>" v="<value>"/>` elements. The kit's
own fixture palette root is `t="b:Folder"` (`fixtures/MinimalPan/MinimalPan/MinimalPan-rt/module.palette:3`), which
`types/structure.md:169-171` forbids and says `scaffold-module.sh` must not emit. (3) The fixture's
`module-permissions.xml` is a bare `<modulePermissions/>`; the course and the New-Module wizard use a `<permissions>`
root with `all`/`workbench`/`station` sections — the kit has no canonical template. (4) Slide Code's `bajadoc`
`includePackage` list is stale (5 phantom packages, 7 omitted), and the kit's fixture uses the same single-package form
with no check.

## Lessons
- The kit must teach the toolchain's own mechanism first (`uberjar`), and third-party plugins only for what it cannot do.
- A kit example that no Tridium artifact matches (class-name palette types, attribute overrides) is a defect; check examples against a shipped jar.
- A fixture is the kit's executable doctrine; when it violates a stated rule, the scaffold propagates the violation to every new module.
- Every `java.*` capability a library uses maps to a permission group; the table belongs next to the library recipe, not in the security chapter.
