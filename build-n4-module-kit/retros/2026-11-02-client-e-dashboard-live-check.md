# 2026-11-02 · kit · client-e-dashboard-live-check

**Session**: live check of the client E dashboard module (facade + servlet + SPA, v1.4.3) on a local 4.15.6.20 station; no code change.
**Delta count**: 33

## What happened
The dashboard's write paths (numeric setpoints, VAV cross-checked limits, AHU reset pulse) had only offline evidence. A fixture of writable test points was created and linked into two facade panels through mcp-n4, and a 59-check API suite plus a headless-browser walk ran against the station. 56/59 passed on the first clean run; the 3 failures were late pulse releases: with per-request timestamps through the dashboard's own API, 4 of 20 releases came at 7.5–8.4 s instead of 5 s (station medium-timer queue), so a first "observer artefact" reading was withdrawn. One real UI defect was found (setpoint fields stuck on "no response" after a reset pulse), and official docs added one real field risk (min-on/min-off timers versus the pulse).

## Evidence
- Suite log: 59 checks; sections connection, security (11 refusals), AHU write + three-place read-back, VAV bounds 18..26 incl. 17.99/26.01, concurrency (one 423 busy), pulse (2×), masking at in10, read-only source, end state. `[ev: session scratch fulltest.log]`
- Pulse timings: 15 presses (idle 90 s, idle 5 s, 3 concurrent writers): 4.6–5.3 s. `[ev: session scratch pulsetime/pulseload/pulseidle]`
- UI defect: after `/api/ahu/pulse`, every setpoint of the same form renders "Sin respuesta de la estación" until the view is reopened (headless screenshots before/after). Matches the open review advisory R3-update-resets-busy-form.
- `in8` refused a link: `Flags.READONLY` on in1/in8 of every writable and in6 of BooleanWritable. `[ev: corpus control-rt BNumericWritable.java:107-110]`
- min-on/min-off timers hold each Out change at level 6. `[ev: niagara-help 4.15.6.20 User/aMinOnMinOffTimes.txt:9-11]`

## Lessons
- A refusal the module makes on purpose (`limits-unknown`, `masked`) is a PASS only when the fixture provides every partner it needs; otherwise the test is wrong, not the module.
- Never measure timing through a tool whose own session can go cold, and never call a late result an observer artefact until per-request timestamps prove it.
- Official docs can add field risks a live fixture never shows (min-on/min-off timers); read the point-type guide before trusting a pulse design.
