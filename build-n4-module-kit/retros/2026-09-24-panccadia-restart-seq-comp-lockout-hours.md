## What happened
Live evidence on 2026-09-24 (`condenser3=true`, `condenser3Fault=true`, `amps3=0.11`,
`stagesOn=3`) showed a burned compressor still commanded and counted as a running stage,
and persisted `condenserNHours` slots reading ~10.6 h against a known ~65.5 h from
2026-09-06 — proof that a non-clean restart (watchdog crash, no station save) loses
run-hour history even though the slots are non-TRANSIENT. `BEvaporatorUnit.applyRunCmd`
was also found to assert `evapOut` in the same scan as `valveOut` after a restart when
`fanRunMode == continuous`, bypassing the valve-first startup the user wants after any
restart. The three fixes (T1/T3/T4) plus two review rounds (six then two advisories,
one CRITICAL requiring a bounded correction) exercised the kit's build/lint/schema-risk/
RDD-correction machinery hard enough to surface ten reusable gaps and lessons, listed
below as proposed deltas.

| Δ5 | **New doctrine — persisted accumulator survives a crash restart via a file-backed backup, not a station save.** A non-TRANSIENT slot (e.g. compressor run hours) only reaches disk on an explicit station save; a watchdog crash/restart with no save loses everything since the last save (live: ~65.5h -> ~10.6h). | Δ6 | **New doctrine — atomic file replace on Windows needs a 3-candidate (dest/.bak/.tmp) protocol, not a naive tmp-then-rename.** `BFileSpace.move()` is backed by `File.renameTo()` (`BFileSystem.java:429`), which SILENTLY OVERWRITES an existing destination on POSIX but FAILS (returns false, throws) on Windows when the destination already exists. A naive "delete dest, then move tmp->dest" leaves a window with zero valid copies if a crash lands between the delete and the move. Proven-safe protocol from this session (`CompHoursBackup.atomicReplace`, `1d4cb62` correction): rename `dest`->`.bak` FIRST (never delete before the new content is safely staged); clear a STALE `.bak` before that rename-away (Windows `renameTo` also refuses an existing `.bak` destination — the exact bug the correction fixed); move `.tmp`->`dest`; best-effort delete `.bak` only after a successful move; on a failed move, best-effort restore `.bak`->`dest` and KEEP `.tmp` (never delete on failure); `seedHours()`/equivalent readers must consider all three candidates (dest/.bak/.tmp), never trust only the resolved `dest` file. Test fakes for this pattern must model Windows rename-refuses-existing-destination semantics, not POSIX overwrite semantics, or the tests give false confidence. | `types/logic.md` § "Restart & persistence" (new recipe, adjacent to Δ5) | `[ev: Cliente/panccadia-leon/odd/tasks/restart-seq-comp-lockout-hours.md T6 "R3-hours-backup-rename-overwrite", T7 "R3-backup-delete-before-move-loses-last-good", "T7 correction" section]` |

## Lessons
- A field workaround or a silent misclassification (a false lint FAIL, a hand-edited facet call) is a signal the lint itself has a gap — fix the lint, not just the call site, whenever avoiding a false positive requires a source-level workaround (Δ1, Δ4).
- "Non-TRANSIENT" and "survives a crash" are not the same guarantee — only a station save persists a slot; a crash restart needs an independent file-backed path (Δ5, Δ6).
- Windows `File.renameTo` semantics (refuses an existing destination) are the default failure mode to design for on this client's stations, not the exception — test fakes must model Windows behavior, not POSIX (Δ6).
- An RDD bounded-correction budget counts every changed line including the ODD progress note, not just the code fix — keep correction notes minimal and plan headroom before writing them (this session's first correction draft was 219 lines against a 200-line budget and had to be condensed to 176 to land).
- A release/unblock predicate driven by "did this already happen" must be backed by an observed flag set at the moment it happens, never reconstructed from configured durations after the fact (Δ9).
