# Retro — DashboardPan `-ux` direct build (2026-09-01) — PROPOSED kit deltas

Status: **propose-never-apply**. A human folds these into `types/dashboard.md` / `METHODOLOGY.md` / `build-verify.md`.
Context: rebuilt only the `-ux` (frontend/servlet) after UI-only edits (SVG plano fix + label repositions). Java-8 + jar, bytecode 52, signed. No `-rt` change.

## What this build PROVED (seeds for the kit)

1. **NO mirror for a build. Build DIRECTLY against the real `niagara_home`.** Operator correction, confirmed against bitácora §3: the proven build is
   `./gradlew :DashboardPan-<m>:jar -Pniagara_home=/mnt/c/Honeywell/OptimizerSupervisor-N4.14.0.162 -Porg.gradle.java.installations.paths=/usr/lib/jvm/java-8-openjdk-amd64`
   The Linux **mirror** (`$HOME/niagara-mirror-hon414`) is a mechanism of `deploy.sh` ONLY (so its build+copy loop never touches the live station); it is NOT part of a plain build and must not be introduced when the operator just asks to "compile". Do not create a mirror uninvited.

2. **This project's gradle layout breaks the kit `build.sh` assumption.** `build.sh` expects `<module-root>/<MOD>-<profile>` with `gradlew` in `<module-root>`. DashboardPan is nested: `gradlew` lives in `Dashboard/` (the gradle root) and the profiles are at `Dashboard/DashboardPan/DashboardPan-{rt,ux,wb}`, addressed as gradle projects `:DashboardPan-ux:jar`. `build.sh <…>/DashboardPan DashboardPan` fails "no executable ./gradlew". For a nested/multi-project module, run `./gradlew :<MOD>-<profile>:jar` from the gradle root directly, then run `verify-module.sh` on `build/libs`. **Kit delta:** `build.sh` should detect the gradle root (walk up for `gradlew`/`settings.gradle*`) and accept a `:project:task` form, or the guide should state the nested-layout fallback.

3. **The niagara plugin auto-installs the jar into `niagara_home/modules/` as part of the `jar` task.** If the station is RUNNING, that copy fails hard — `clean` → `Unable to delete file …/modules/<MOD>.jar`; `jar` → `FileAlreadyExistsException … Tried to overwrite the destination, but failed to delete it`. The gradle build reports FAILED, but the artifact in `build/libs/<MOD>.jar` is still fully **assembled and signed** (the copy is the last step, after signing). Confirm with the gate: `verify-module.sh` PASSED (14 classes major 52, `META-INF/NIAGARA4.SF` present, types resolve) on the "failed" build's jar. **Two clean exits:** (a) build with the station stopped (bitácora "con la station detenida") for a green build; (b) for a UX/STORED-for-signing artifact, use the gate-verified `build/libs` jar and treat the `modules/` copy failure as irrelevant (you are not deploying to that supervisor). Skipping `clean` avoids the first delete error but not the `jar` copy error.

4. **Editor/backup files left in `src/rc/` get packaged into the jar.** `processResources` copies ALL of `rc/`, so `index.html.bak` / `index.html.bak2` shipped inside `DashboardPan-ux.jar` (~4.7 MB of dead weight in a ~9 MB jar, and servable at `/<prefix>/index.html.bak2`). Keep `rc/` clean: no `*.bak`, no editor scratch. **Kit delta:** `verify-module.sh` (or the dashboard guide) should flag non-asset files under `rc/` (`*.bak`, `*.orig`, `*~`, `*.tmp`) as a WARN; the dashboard checklist should say "the label editor is preview-only (inject via `dashboard-preview.py --editor`), never a file committed under `rc/`."

## Tooling that helped (seeds for `toolbelt` / `dashboard.md`)

5. **`dashboard-preview.py --editor` (new flag) injects a preview-only label editor** without touching the module: it flips `ui.editPuntos`, adds `edit` to `#frameC`, and gives a drag + live `rx/ry/rlx/rly/rside` readout + copy, plus a "reset localStorage" button (the module's `restaurar()` reloads dragged positions from `panccadia.puntos.v11` and can mask file edits). Reusable for any dashboard whose detail view already carries the drag handlers. **Kit delta:** document `--editor` in `dashboard.md` as the sanctioned way to reposition point/label overlays.

6. **Diagnosing an HMI-only render bug: the panel WebView (i.MX8M, 1280×800 16:10) diverged from desktop Chromium on `object-fit`/`aspect-ratio`.** A plano image (1248×891, 1.40) letterboxed correctly in the simulator but stretched to the 16:10 frame on the panel, while the separate polygon-overlay box (sized by JS `ajustarCaja` contain-math) stayed at contain → the two layers split. **Fix pattern (WebView-agnostic):** put the raster INSIDE the overlay SVG as `<image width=W height=H>` and set the SVG `preserveAspectRatio="xMidYMid meet"`, so image + vectors scale as ONE unit and never depend on `object-fit`/`aspect-ratio`/`ResizeObserver`. **Kit delta:** `dashboard.md` — "overlay vectors on a raster via one SVG (`<image>` + shapes in the same viewBox), not an `<img>` + absolutely-positioned SVG whose box is JS-fitted; the two-layer approach is fragile on embedded WebViews."
