## What happened
Three kinds of finding. (1) Security/signing: six permission groups require a signed module (`requiresSignature()` true in REFLECTION, ACCESS_CLASS, MBEAN_PERMISSION, THIRD_PARTY_PERMISSION, PROTECTION_DOMAIN, HSM_SIGNING) where the kit names three; the 4.14 factory drops such a group with a WARNING ("Skipping element") rather than failing the load, while the devguide says the station halts; any cert trusted by the installation works, not only a "Tridium-trusted" one. (2) Authoring files: the devguide says `module-include.xml` holds only `<types>` (the kit still puts `<moduleParts>` there), external jars use only `uberjar`/`testUberjar` (the kit's main recipe is Shadow + `implementation`), help belongs in a `doc` part of the module (the kit says NEVER), `help.guide.base` is optional (the kit sets it to `module://docUser/doc`, sending vendor help to Tridium's pages), and `-se` means "depends on Java SE APIs", not "server-only". (3) Horizons the kit never mentions (0 kit hits for all): the web session idle timeout is reset by `UserActivityFilter` or the browser activity monitor — not by arbitrary REST polls, which matters for our wall-mounted HMI; module web apps via `WEB-INF/web.xml`; the history `_cfg0` split on an interval or record-type change; exporter `view:` URLs for CSV; js-ux helpers; login branding; popup editors.

## Lessons
- A rule asserted as "fails to load" needs the layer named; the code shows at least two layers (permission factory, cert chain) with different outcomes.
- The devguide's prescriptive shape (doc part, types-only include, uberjar) and Tridium's shipped practice (separate doc modules) can both be legitimate; the kit should say which it chose and why, never "NEVER".
- The highest-value horizon was a behaviour, not an API: whether polling keeps a session alive decides whether a wall HMI logs itself out.
