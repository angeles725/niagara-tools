**Delta count**: 10

## What happened
The kit's examples in these areas contradict the source in ways that change behaviour: the proxy-point example has `readUnsubscribed` send a poll (the contract is "stop polling / unregister"); `subscribed()` is framed as "a remote client watches" when a linked running component is subscribed with no client; the `.nav` example omits the mandatory `version="1.0"` (the decoder throws) and its "static cache never refreshes" gotcha is wrong (the cache re-parses on lastModified change); the `nav:` example lacks its `root:|` base; `BOrd.make` is said to parse and normalize (it only wraps the string); the tag-dictionary recipe names `getRules()`, `SmartTagRule`, a `tagInfoList` slot and a `BNamespace` in `module-include.xml` — none exist as described; the NEQL example is outside the grammar; and `hierarchy:` ORDs are presented as station-usable although they resolve only client-side. Missing capabilities: `getNavChildren()` is permission-blind (no `BNavContainer.filter` rule), `OrdTarget.canRead/canWrite/canInvoke` return true when no security target exists, leases, virtual-component cache tuning, custom ORD schemes, unmounted-tree BQL for tests, NEQL parameters, and the bajaScript Subscriber/tags contracts.

## Lessons
- Example code is the most-copied text in the kit; an inverted example (`readUnsubscribed` polling) outweighs a correct one-line rule two screens later.
- Recipes derived from an earlier retro (organization-tags) carried invented API names forward; a symbol-existence check at fold time would have stopped them.
- "Who can see this" is a separate question from "what exists": nav and ORD APIs both return everything unless the caller filters with its Context.
