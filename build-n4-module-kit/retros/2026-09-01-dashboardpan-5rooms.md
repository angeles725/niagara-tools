# Retro — DashboardPan 3→5 rooms + deploy/signing (2026-09-01) — PROPOSED kit deltas

Status: **propose-never-apply**. A human folds these into `types/dashboard.md` / `build-verify.md` / `METHODOLOGY.md`.
Context: extended an already-built dashboard module (facade `-rt` + servlet/SPA `-ux`) from 3 to 5 cold rooms by adapting an operator-built standalone HTML (v17), removed the point editor, extended the Java facade, built against Honeywell 4.14, and unblocked a Workbench signing failure. Clean Java-8 + slotomatic + jar (bytecode 52, baja 4.14, signed).

## What this build PROVED (seeds for `types/dashboard.md`)

1. **A data-driven SPA scales room-count by SWAPPING DATA BLOCKS, not touching render code.** The module's render (`CUARTOS.forEach` builds the room list, setpoints page, plano polygons, and detail views; `SENSORS.map` builds telemetry) is room-count-agnostic. Going 3→5 rooms was: replace `CUARTOS` (add `color`/`w`/`h`/`foto`/`poly`), `SENSORS`, `FANS`, the plano `<img>` src, and `viewBox`/`IMG_W`/`IMG_H` — zero changes to `dibujarZonas`/`renderChart`/`selectRoom`/setpoint logic. RULE: before hand-editing a dashboard SPA, check whether the thing you want to change is DATA (an array the render iterates) or CODE. If data, it's a splice. Verify with `node --check` on the extracted `<script>` blocks after.

2. **Keep the module as the SKELETON, port only the operator's new DATA in.** The operator iterated the *design* in a standalone HTML (v15→v17: 5 rooms, renders, editor removed). The module already had the *integration* (kiosk CSS, `/api/equipment` wiring, Niagara status classes, alarms, setpoint save). Correct merge = module index.html as base, splice v17's calibrated data blocks in, remap the sim ords (`TE-XX/SpaceTemp`) to the module's Niagara ords (`CuartoN/{zone|evap|resist}Temp{n}`). Do NOT rebuild the module from the standalone — you lose the integration layer. (Learned the hard way earlier: rebuilding from the standalone was rejected by the operator.)

3. **Facade room-count is also data-driven.** `DashboardReader.ROOMS = {"Cuarto1".."CuartoN"}` drives the whole `/api/equipment` walk; the servlet/dispatch/RBAC take an ARBITRARY ord (no hardcoded rooms). Extending the facade = add one `@NiagaraProperty(name="CuartoN", type="BRoomPanel")` per room (slotomatic regenerates the AUTO region + type hash) + one entry in the reader array. Every `BRoomPanel` already carries all point slots, so the extra rooms expose the full slot set for free.

4. **Preview iterates frontend WITHOUT a build.** `dashboard-preview.py --rc <module>/src/rc` serves the real `rc/` source live; a frontend edit (here: moving a zone label) is visible at `:PORT/hmi` on refresh — no build/sign/deploy. Confirms the kit's "preview before compiling" gate; extend it: use the SAME running preview to iterate label/CSS/layout tweaks, only build when the Java or the deployable artifact must change.

5. **Zone-label overlap on the plano = centroid collision; fix with an optional per-room label override.** `dibujarZonas` places each room's label at its polygon centroid. Adjacent or concave rooms (here Cuarto 2 vs the L-shaped Cuarto 5) get near-identical centroids → labels overlap. Fix without touching geometry: add an optional `lbl:[x,y]` (in %) to the room object and `cu.lbl ? cu.lbl : centroid` in the label placement. Minimal, data-only, reversible.

## Build-target & deploy lessons (seeds for `build-verify.md`)

6. **`gradle.properties` niagara_home can LIE about the real target — verify against the pinned plugin version.** DashboardPan's `gradle.properties` said `C:\Niagara\iC-Niagara-4.13.2.18` (iSMA), but `settings.gradle.kts` pins `gradlePluginVersion = "7.6.17"`, which exists ONLY in Honeywell 4.14's `etc/m2` (4.13.2 ships 7.3.x). So the module MUST build against Honeywell 4.14. RULE: the true build target is `intersection(niagara_home has the pinned plugin, station accepts the stamped baja)`. Check the pinned version in `settings.gradle.kts` and `ls <niagara_home>/etc/m2/repository/com/tridium/niagara-module/.../` before trusting `gradle.properties`.

7. **A Windows `niagara_home` path breaks the m2 repo under WSL.** Building on WSL with `niagara_home=C:\...` makes gradle resolve the plugin repo as `maven(file:/C:/Niagara/...)` → "plugin not found" (Linux can't read `file:/C:/...`). Always override with the `/mnt/c/...` mount: `-Pniagara_home=/mnt/c/Honeywell/OptimizerSupervisor-N4.14.0.162`.

8. **The niagara-module plugin INSTALLS the jar into `<niagara_home>/modules` during the build.** Building with `-Pniagara_home=<the live station install>` deploys in one step (jar lands in `build/libs` AND `<station>/modules`, md5-identical). This ONLY works with the station STOPPED — a running station locks the jar and `clean` fails. To deploy without stopping a live supervisor, build against a mirror (retro 2026-08-31 lesson 8) then copy `build/libs` → station. A reusable `deploy.sh` (modeled on the chihuahua reference) does build+backup+copy+md5-verify.

9. **A Honeywell OptimizerSupervisor station ACCEPTS gradle's per-machine DEV cert — Workbench re-signing is NOT required for the supervisor.** Evidence: the chihuahua reference module runs on the same supervisor and its `deploy.sh` only builds (gradle auto-signs DEV) + copies — it NEVER re-signs with a project cert. Contrast with a JACE field controller, which enforces the project CA (angelessigner) — that is why ColdRoomPan (JACE-bound) was re-signed but DashboardPan (supervisor-bound) need not be. RULE: check the DEPLOY TARGET's signing policy before assuming a Workbench re-sign is needed; a dev supervisor commonly accepts the DEV cert.

10. **Workbench `JarFileSigner` "invalid entry compressed size (expected N but got M)" is a DEFLATER MISMATCH between the JDK that BUILT the jar and the Workbench JDK — the reliable fix is to repackage the jar STORED (no compression).** The `ZipException` fires in `ZipOutputStream.closeEntry` while Workbench re-writes each entry: gradle (WSL OpenJDK 8) stored one compressed size; Workbench (Windows Zulu 8) re-deflates the same bytes to a size a few bytes smaller → mismatch (observed "expected 422 got 420", "expected 421 got 418" — different entry each build, always off by 2–3 bytes).
   - **CORRECTION of a 2026-08-31 hypothesis.** This is NOT transient build-state; a `clean + slotomatic + jar` rebuild does NOT fix it (same WSL deflater → same size → same mismatch, it recurs). And it is NOT testable locally with `jarsigner`: the WSL `jarsigner` uses the SAME deflater that built the jar, re-deflates to the SAME size, and reports "jar signed" while Workbench still fails. **Local jarsigner is a FALSE NEGATIVE for this defect — do not use it to claim Workbench-signability.** (The "Zulu-vs-Linux zlib" idea that was walked back in an earlier session was right; the counter-argument "chihuahua uses Linux OpenJDK and never fails" does not disprove it — chihuahua never re-signs in Workbench, so it never re-deflates.)
   - **Sound fix — mismatch impossible by construction, verifiable with `unzip -v` (0 `Defl:` entries):** repackage STORED, manifest + signature first so the jar stays valid:
   ```
   cd ex && unzip -q <jar>
   zip -0 -X -D out.jar META-INF/MANIFEST.MF
   [ -f META-INF/NIAGARA4.SF ]  && zip -0 -X -D out.jar META-INF/NIAGARA4.SF META-INF/NIAGARA4.RSA
   zip -0 -X -D -r out.jar . -x META-INF/MANIFEST.MF META-INF/NIAGARA4.SF META-INF/NIAGARA4.RSA
   ```
   STORED keeps uncompressed content byte-identical, so the existing DEV signature stays valid (`jarsigner -verify` → "jar verified") AND Workbench can re-sign without the mismatch. Cost: bigger jar (ux 6.9MB→9.1MB). Since the supervisor already accepts the DEV-signed jar (retro 9), STORED only matters when you MUST re-sign in Workbench. **[CERT-live 2026-09-01] the operator signed both STORED jars in Workbench with NO `ZipException` — the STORED repackage fixes the signing defect, field-confirmed.** TODO(verify): confirm a STORED module jar LOADS on the running station (standard zip; expected fine, not yet field-confirmed).
