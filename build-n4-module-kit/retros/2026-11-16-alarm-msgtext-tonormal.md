# 2026-11-16 · kit · alarm-msgtext-tonormal

**Session**: rows B1 and M7 of a client A live retro: an alarm's `msgText` is rewritten by the toNormal
transition, so a value meant to survive normalization must live in a persisted slot.
**Delta count**: 2

## What happened
On client A's station (4.15.3.28) a compressor over-amps alarm raised and cleared within three minutes. Its
alarm extension had a `toOffnormalText` quoting the source's amps slot through a `%parent...%` path, set two
days earlier so the record would keep the amps of the event. The record read after normalization had
`msgText=` empty; only the 1-minute history showed about 23 A. The behaviour was already on record in our
research memory for the driver ping alarm (pingFail text replaced by pingSuccess on recovery) and was missed.

## Evidence
- niagara-help source 4.14.0.162, `alarm-rt/javax/baja/alarm/BAlarmDatabase.java:254-271`: `toNormal` copies
  each open record, sets `sourceState=normal`, `normalTime`, and `setAlarmData(BFacets.make(old, normal))` on the
  same UUID; `AlarmSupport.java:491` does the same merge in its to-normal transition.
- `baja/javax/baja/sys/BFacets.java:665-690`: `make(orig, toAdd)` keeps keys only in `orig` and takes `toAdd`'s
  value for a key in both.
- `alarm-rt/javax/baja/alarm/ext/BAlarmSourceExt.java:1619-1621`: on a normal transition the ext always puts
  `msgText` = `getToNormalText().getFormat()`; the slot defaults to `BFormat.make("")` (`:668`). So the merge
  overwrites the offnormal text with an empty string.
- `alarm-rt/javax/baja/alarm/BAlarmSourceInfo.java:420-430`: the `AlarmSupport` path writes `msgText` only when
  the state's text is non-empty.
- Guide `User/BFormatAlarmExtensionExample-8FD6BF0E.txt:71` (`nh guide-search "alarm text properties are
  relative"`): "All the alarm text properties are relative to the alarm record component generated by an alarm,
  and not to the alarm extension"; `:89` says `%parent.displayName%` gives no useful result there. The
  `%parent...%` path in the live text could not resolve even before normalization.
- The same lines are in the decompiled 4.14.0.162 jar (vineflower `BAlarmSourceExt.java:815`,
  `BAlarmDatabase.java:153`). The 4.15 source was not read; the live 4.15.3.28 record agrees [INFER: same path].

## Lessons
- A behaviour already in research memory must be searched before an alarm text design, not after the record is
  read live.
- An alarm text that names a source slot is wrong twice: it does not resolve against the record, and the
  normal transition replaces it.
