# BUILD-STATE — the build-session continuity ledger

Where the last build session for each module left off. A new session READS this at orient
(`BUILD-LOOP.md` §0.a) and UPDATES it at close (`BUILD-LOOP.md` §7). This is the kit's
"where did we leave off" registry — the build-loop analog of research-sdd's FOCUSES +
RESEARCH-STATE registries, collapsed into ONE file because the build corpus is a handful of
modules, not sixty focuses.

## How to read this file

- **One `build-state.v1` envelope per module**, between `<!-- build-state.v1 -->` and
  `<!-- /build-state.v1 -->`. Fields are `key: value`; a parser strips blank lines, the
  `open_issues:` list items, and any trailing `# comment`.
- **GATED vs DECLARED — never label a gate that cannot run.**
  - **GATED** (`retro_required`, `retro_pending`): machine-enforced, but ONLY for KIT-local
    changes inside the `niagara-tools` repo — that is the only diff the enforcement check
    (build-n4-retro-gate / PR2) can see.
  - **DECLARED** (`module_repo`, `module_root`, `last_build`, `bytecode_major`, `signed`,
    `verify_gate`, `deployed`, `target_station`, `pure_tests`, `last_commit`): these describe
    module trees that live in SEPARATE repos (`Cliente/Leon-Guanjuato`, `Cliente/Honeywell/MX60`).
    A `niagara-tools` check cannot see those diffs, so they are RECORDED here, not gated.
- **Unknown is honest.** A DECLARED field with no authoritative value is `unknown`, never a guess.
- **Deployed-baseline fields (optional, DECLARED) — answer "which tree is on the station?" without Software Manager:** `deployed_jar_sha256`, `deployed_build_millis` (the installed jar's `module.xml` `buildMillis`), `deployed_source_commit` (the `module_repo` commit that built it), `deployed_baseline_date`. A `vendorVersion` bump alone does not answer this: a BEHAVIOR-only fix (no schema change) can leave two source trees at the SAME version, and Software Manager reports "Up to Date" against whichever jar is already installed regardless of which tree built it. Record these fields at every deploy so a later session can answer "which tree is actually on the station" from this file instead of comparing candidate checkouts by hand. See the ColdRoomPan canonical example below for the field shape; `unknown` is honest for a deploy that predates this template. `[ev: retro panccadia-defrost-sequencing-hmi-reload-deltas Δ3]` (the gap this template closes is documented at `[ev: retro panccadia-defrost-sequencing-hmi-reload-deltas Δ2]` — the CompPan leon/leon2 ambiguity).
- **`source_of_truth` (DECLARED, required for every module): `<path>@<branch>@<commit>`** — WHICH checkout is authoritative for this module: `<path>` is the client tree (as in `module_repo`), `<branch>` the branch builds come from, `<commit>` the commit last confirmed as the source of record. Update it in the SAME session that moves the authoritative tree, branch or commit — never only in session memory (the authoritative source of one client moved three times in three weeks and sessions kept rediscovering it). `unknown` stays honest, for the whole field or any part (`<path>@unknown@unknown`). `scripts/check-client-source.sh --build-state BUILD-STATE.md --module <MOD> <module-root>` (BUILD-LOOP §0.b) compares a checkout against it. `[ev: retro client-source-of-truth Δ2]`
- **`ui_profile` (DECLARED, required for every module with a `ux` profile): `hmi | lan | both | unknown`** — who opens the dashboard; it selects which profile-tagged rules apply. The values, the `both` single-build/two-entry rule and `unknown` are defined ONCE in `types/frontend-standard.md` § Profiles (single source; `types/dashboard.md` and this file only reference it). Record it in the module's envelope (and its module docs) the first time the `-ux` is touched. `[ev: retro dashboard-deployment-profiles Δ1]`
