Usage: ng-deploy.sh [OPTIONS]

Deploy a Niagara N4 module jar to a station modules directory.

Options:
  --mode <A|B|C>           Build mode (default: A)
                             A = rt + ux jars (both)
                             B = ux jar only  (JS/CSS/Java servlet changes)
                             C = rt jar only  (Java BComponent changes)
  --env-file <PATH>        Source env from PATH instead of .env.local
  --no-deploy              Build only; do not copy or verify (jars stay in build/libs/)
  --no-backup              Skip the backup step (opt-in; prints a one-line rollback WARN).
                             No companion flag required — the default backup is a safe
                             lightweight one, so skipping it is a plain choice.
  --full-backup            Back up the WHOLE modules dir (every sibling module), old behavior.
                             Default is lightweight: only this module's own -rt/-ux/-wb jars.
  --keep <N>               Backups to retain per module (default 3); older ones auto-purged.
  --i-know-what-im-doing   Accepted no-op (kept for backward compatibility; --no-backup no longer gates)
  --with-slotomatic        Run :MODULE-rt:slotomatic (and :MODULE-ux:slotomatic when -ux is annotated) BEFORE build_jars (opt-in; ignored on mode B)
  --strict-slotomatic      Abort with exit 15 if annotation changes detected without --with-slotomatic
  --no-gate                Skip the verify-module.sh gate (default: on for mode A/C). Without
                             --no-gate a MISSING gate binary blocks the deploy (exit 50).
                             The gate is run with --src and with --expected-signer <signer>: see
                             "The signer the gate expects" below.
  --first-deploy           The module was never deployed: skip the schema-risk precheck (no
                             baseline to diff). Same as FIRST_DEPLOY=1 in the env file
                             (an exported FIRST_DEPLOY in the shell is ignored).
  --accept-lossy           Proceed on a schema-risk LOSSY verdict (an OUTAGE always blocks).
  --gradle-prop <k=v>      Repeatable; forwarded to every gradlew call as -Pk=v, as build.sh forwards it
                             (niagaraSigningAlias=<alias>, niagaraSigningProfile=<profile file>). The gate
                             expects the last niagaraSigningAlias given. Not k=v: exit 10.
  --install-into-home      Build although NIAGARA_HOME is a real installation and not a mirror (no
                             .niagara-mirror): the build then replaces the module's jars in its modules/
                             directory before any check runs. Command line only; build.sh has the same option.
  --help                   Print this help and exit 0
  --version                Print SCRIPT_VERSION and exit 0

Required env vars (from .env.local or --env-file):
  MODULE_NAME, GRADLEW_PATH, NIAGARA_HOME, NIAGARA_USER_HOME,
  JAVA_HOME, STATION_MODULES_DIR
  EXPECTED_RT_TYPES  (required for mode A or C)
  EXPECTED_UX_TYPES  (required for mode A or B)

Required for mode A or C unless --first-deploy:
  SCHEMA_BASELINE_DIR  — the DEPLOYED -rt source baseline (module-include.xml + *.java), diffed by
                         schema-risk.sh against the -rt module dir before the copy (build-verify.md
                         § Schema-risk deploy workflow)

Backups:
  A backup is written to _backups/ under the working directory (the directory ng-deploy.sh is run from), as
  _backups/<MODULE_NAME>-pre-<YYYYMMDD-HHMMSS>.tar.gz; the newest KEEP_N of the module are kept. It is written,
  and the older ones purged, just before the copy, after the build and every check (with --no-deploy: after
  the build), so a run that stops before then leaves _backups as it was. When STATION_MODULES_DIR is
  <NIAGARA_HOME>/modules it holds the jars that were there before the build, under their jar names. The step
  prints "backup: <archive>" and "backup ok: <archive>" only when it writes one: for a module with no
  -rt/-ux/-wb jar in STATION_MODULES_DIR it prints "backup: no existing <MODULE_NAME>-{rt,ux,wb}.jar in <dir>;
  nothing to archive" and creates nothing. To restore a default (lightweight) backup, with the station stopped:
    tar -xzf _backups/<archive> -C "$STATION_MODULES_DIR"
  and a --full-backup one, which holds the modules directory itself:
    tar -xzf _backups/<archive> -C "$(dirname "$STATION_MODULES_DIR")"
  Restoring the previous jar is for a deploy that never ran in the station; after the station loaded the new
  version, recover by deploying a higher version (BUILD-LOOP.md § 6: roll-forward).

After a deploy:
  A deploy that went through (exit 0) ends with, after "station restart required (Java classes deployed)" or
  "browser hard-reload only (no station restart needed)":
    done:   the jars it copied and the directory they are in
    signer: who signed each jar (or that it carries no complete signature). The gate checks who signed, not
            whether the station trusts that signer: the station decides when it loads the module
    next:   (modes A and C) restart the station. ng-deploy does not look at whether a station is running, and
            stops or starts none
    next:   (modes A and C) the console check to run after the restart (toolbelt/triage-console.sh)
    undo:   how to remove the module again: take its components out of the station, stop it, delete the jars
            (it points at the backup only when this run wrote one)
  A run that deployed nothing (--no-deploy, any failure) and one that could not record its commit (exit 41)
  print none of these.

NIAGARA_HOME and its modules directory:
  gradle's :jar step installs the built jars into <NIAGARA_HOME>/modules before any check of the deploy has run,
  and in a real installation that directory is a station's. So NIAGARA_HOME must be a mirror (a directory made
  by build-n4-module-kit/toolbelt/mirror-niagara-home.sh <niagara_home> <mirror_dir>, which holds .niagara-mirror);
  a NIAGARA_HOME that is a directory without that file is refused before the backup and before gradle runs
  (exit 10) unless --install-into-home is given. A mirror build gets the isolation build.sh gives it (one
  shared rule, go/internal/gradleenv): JAVA_TOOL_OPTIONS += -Duser.home=<mirror>/.mirror-user-home (and
  -Dmaven.repo.local=$HOME/.m2/repository unless set), GRADLE_USER_HOME pinned, and --no-daemon on every gradlew
  call, so the signing plugin cannot read the real ~/.tridium keystore; a mirror path or $HOME with whitespace
  is exit 10 before gradle runs. In both cases the module's own -rt/-ux/-wb jars there are moved
  aside (<jar>.ng-deploy-old) before the build, and when the build, a check or the copy fails, or SIGINT or
  SIGTERM arrives before the copy, they are moved back and the jars the build added are removed: the directory
  holds what it held before the build, and a NOTICE says so ("the jars the build installed ... were taken out
  again" only when every jar was put back or removed; one that names the jar of another origin left in place
  otherwise; or, when the build installed none, "the build installed no jar ...; the module jars moved aside for
  it were moved back"). A jar the directory did not have is removed only when it is the jar this run built
  (the bytes of build/libs): any other is left where it is, with a WARN that names it. A jar that could not be moved back or removed is an ERROR
  line that names it jar by jar, as for exit 40; the exit code stays that of what failed. After a deploy that went through (or --no-deploy)
  the built jars stay there. When STATION_MODULES_DIR is that same directory, however it is spelled (a relative
  path, symbolic links, another case on a mount that ignores case: the file system is asked), a line says so,
  the version-bump precheck compares with the jar that was there before the build, and the copy step copies
  nothing: it checks that the directory holds the jars of build/libs. Something that is not a jar file under
  the name of a jar of the mode is refused there as the copy refuses it (exit 40), before the build.

The run lock:
  Two runs on one modules directory lose jars (each puts back, or removes, what the other moved). A run
  therefore holds a lock file, .ng-deploy.lock, in every modules directory it changes: <NIAGARA_HOME>/modules,
  then STATION_MODULES_DIR when that is another directory and the run deploys (always in that order). The
  locks are taken before the run looks at either directory and removed when it ends, however it ends: success,
  any failure, SIGINT or SIGTERM (from its first lock on, the run catches both and ends with 130 or 143 after it
  put things back). The file holds four lines: "pid <pid>", "host <host>", "started <UTC time>", "command
  <program>" (the name ps -p <pid> -o comm= prints for the run: ng-deploy).
  A lock that is there stops the deploy (exit 10): "another ng-deploy run holds <file> (pid <pid> on host
  <host>, started <time>, <age> ago): ...". A lock is never removed for the run that made it, so a run that was
  killed (SIGKILL, power) leaves its lock, and the next deploy refuses: check on <host> that ps -p <pid> -o
  comm= does not print <program> (a pid that is alive can be another program's, given again after the kill),
  delete the file, deploy again; a lock of this host whose pid runs another program gets a second line, "pid
  <pid> runs <other>, not an ng-deploy run: ..."; a .ng-deploy-old file that run left beside it is refused
  next, with its own way out. The lock is an exclusive file creation, not flock, so it also holds on a Windows
  mount: the run writes it in a temporary file beside it (.ng-deploy.lock.<random>.tmp) and hard-links that to
  .ng-deploy.lock, so a run that loses the race reads a whole lock. When the link fails for another reason than
  a lock that is there (a file system without hard links, too many links), the lock is made in two steps,
  created and then written, and one NOTICE per run says so once the run holds its lock: a run that starts in
  the same instant can find it empty. A temporary lock file older than a minute is one a killed run left: the
  next run removes it with a NOTICE. A directory the run is not allowed to write gets no lock: the run cannot change it either.

The signer the gate expects:
  The verify-module gate is told who must have signed the jars, resolved as toolbelt/build.sh resolves it: the
  niagaraSigningAlias gradle property (ORG_GRADLE_PROJECT_niagaraSigningAlias in the environment or the env
  file, else GRADLE_USER_HOME/gradle.properties, else gradle.properties beside gradlew), else the one signer of
  the module's jars of the mode that were in <NIAGARA_HOME>/modules before the build, never the signing
  plugin's default development signer (NIAGARA4). A jar signed with another key then fails the gate (exit 50).
  When neither names a signer the gate accepts any signature and, after the gate's rows, the deploy prints
  "WARN no niagaraSigningAlias is configured and no deployed jar gives a signer, ..." (or "... the deployed
  jar itself carries the signing plugin's default development signer (NIAGARA4), ..."); the exit code is the
  same with or without the warning.

The env file and the flags:
  An option variable in the env file (MODE, KEEP_N, FULL_BACKUP, NO_DEPLOY, WITH_SLOTOMATIC, STRICT_SLOTOMATIC,
  FIRST_DEPLOY, ACCEPT_LOSSY) sets that option; the flag of the same option, when given, wins over it.
  NO_GATE=1, NO_BACKUP=1 and INSTALL_INTO_HOME=1 are refused in the env file (exit 10, with file and line) unless
  --no-gate, --no-backup or --install-into-home is given. Only these three keys are refused: MODE=B (a mode without the gate) and
  VERIFY_MODULE_BIN in the env file are read as before.

Optional:
  BUILD_ID             — when set, verifies index.html in ux jar contains ?v=$BUILD_ID
  SLOTOMATIC_DETECTION — warn|strict|off (default: warn); controls annotation-change heuristic
  FULL_BACKUP=1        — same as --full-backup (whole modules dir)
  KEEP_N               — same as --keep N (backups to retain per module; default 3)

Exit codes:
  0   success (or --help)
  10  missing required env var, invalid path or option value, or an env file that is a directory, cannot be
      read, holds a line that is not a plain assignment, or sets NO_GATE=1 / NO_BACKUP=1 without the flag;
      or a modules directory another run holds the lock of (.ng-deploy.lock: "The run lock" above);
      or, after the checks and before the copy, a .last-deploy-sha that is a directory or cannot be written
      (nothing was copied; SLOTOMATIC_DETECTION=off makes the record optional)
      or, before the backup and before gradle runs, a NIAGARA_HOME that is a directory and not a mirror without
      --install-into-home, or a <jar>.ng-deploy-old file of the module in <NIAGARA_HOME>/modules (a run that was
      killed left it; rename it over its jar or delete it); or, just before the build, a jar of the module there
      that cannot be moved aside
  15  slotomatic failed or skipped a file (METHODOLOGY K15), or annotation changes detected in strict mode;
      strict mode also refuses when the detection could not run, which includes a .last-deploy-sha that is
      malformed or names a commit git does not know (outside strict mode: a NOTICE, and the diff starts at HEAD~1)
  20  backup failed (tar returned non-zero); nothing was copied
  21  the backup was written, but an older backup of the module could not be purged (nothing was copied)
  30  build (gradlew) returned non-zero
  40  copy of the jars to STATION_MODULES_DIR failed. The copy is all-or-nothing: every jar is staged beside its
      target (<jar>.ng-deploy-new), the station's jars are moved aside (<jar>.ng-deploy-old), the staged ones
      renamed in, and a failure is undone from the jars aside, with or without a backup. The ERROR line says
      what the station holds: the jars it held before the deploy (nothing to do); or, only when a jar aside
      could not be moved back, which jar is NEW or MISSING and the .ng-deploy-old file that holds its previous
      bytes, to rename back before the station restarts. Refused here before anything is copied or changed:
      a station that holds a .ng-deploy-old file for the -rt or -ux jar (a deploy that did not finish left
      it; ng-deploy never deletes one it did not create: rename it over its jar to go back, or delete it to
      keep what is there), and a directory or a dangling link under the name of a jar
      When STATION_MODULES_DIR is <NIAGARA_HOME>/modules nothing is copied; exit 40 is then a jar of the mode that
      the build did not leave there with the bytes of build/libs (the previous jars are put back). A directory
      or a dangling link under the name of a jar of the mode in <NIAGARA_HOME>/modules is exit 40 before the
      build in every case ("build refused for <jar>"). A jar that could not be replaced or moved (exit 40, or exit 10 for a
      jar of <NIAGARA_HOME>/modules) with Device or resource busy or Text file busy, or with Permission denied or
      Operation not permitted in a directory this user may write (how a Windows drive mounted in WSL answers for
      a jar a running station holds open), is followed by the line "a running station or Workbench holds its
      module jars open; stop it and run again". The same two errors in a directory this user may not write are
      followed by "<dir> does not let this user create, rename or remove files (no write permission): ...". Before the build, each
      station jar the run will replace is renamed to <jar>.ng-probe and straight back: a jar that cannot be moved
      is exit 40 there, with no build ("copy refused: <jar> in <dir> cannot be moved"); one that could not be
      moved back is named with both paths and the rename to make. SIGINT, SIGTERM or SIGHUP during the two moves
      waits until the jar is back, then ends the run (128 + the signal), as one does while the probe looks at a
      jar it does not move. A <jar>.ng-probe a killed run left is moved
      back under the jar's name when the jar is missing (a NOTICE says so); beside the jar it is exit 40 with the
      fix: compare the two, keep the one the station should load under the jar's name, delete the other; a
      <jar>.ng-probe that is not a regular file (a directory, a symbolic link) is exit 40 naming what it is,
      left in place: a run never leaves one
  130, 143  SIGINT or SIGTERM during the copy: the copy was undone as for exit 40 and the line says so; or between
      the first run lock and the copy: nothing was copied, <NIAGARA_HOME>/modules was put back and the locks
      were removed
  41  the jars were copied, but the deployed commit could not be read (git rev-parse HEAD) or written to
      .last-deploy-sha (a record that could be written before the copy and no longer can): restart as the
      last line says, then fix the record (SLOTOMATIC_DETECTION=off makes it optional). A working directory
      that is not a git repository (git says "not a git repository" and no .git is there or above) has no commit
      to record: a NOTICE says so and the deploy ends 0. A repository git refuses to open (dubious ownership, a
      corrupt .git) is still exit 41
  12  schema-risk precheck impossible: no SCHEMA_BASELINE_DIR and no --first-deploy (mode A/C)
  50  verify failed: type count mismatch (a jar with no type entry counts 0), a module.xml that unzip cannot
      read, BUILD_ID not found, or verify-module gate failed/missing (a jar not signed by the expected signer
      fails the gate)
      (every check runs on build/libs before the copy: nothing reaches STATION_MODULES_DIR, and
      <NIAGARA_HOME>/modules is put back as it was before the build)
  51  version-bump precheck: the built jar's content differs from the deployed jar but its vendorVersion did not
      change (numeric per component, a missing component = 0: 1.3 -> 1.3.0 is NOT a bump). Content is the set
      of entry names and the bytes of every entry, apart from what a rebuild of unchanged sources changes: the
      signature files (META-INF/*.SF, *.RSA, *.DSA, *.EC), the digests of the manifest's per-entry sections,
      and the values of the buildMillis and buildHost attributes of the root element of META-INF/module.xml
      (when and on which machine it was built). Those two values are cut out of the root element's start tag,
      wherever they stand among its attributes, and every other byte of module.xml is compared as it is: the
      same names on another element, the order of the attributes and their quotes are content. Two jars that differ in nothing else
      are the same module: the deploy goes on ("version-bump ok (<jar>: vendorVersion still <v>, and the same
      content ...)"), so a deploy can be repeated unchanged
  52  version-bump precheck cannot verify (a vendorVersion is unreadable, the two differ in a non-numeric suffix,
      the build left no jar in build/libs, or, under the same vendorVersion, a jar whose content cannot be read:
      not a zip, no entry, two entries under one name, an entry that fails its CRC, a module.xml with no
      root element; or a jar over a limit of the comparison, which reads entries in pieces and never whole:
      more than 2147483648 bytes (2 GiB) of declared content in one jar, or a MANIFEST.MF or module.xml over
      8388608 bytes (8 MiB))
  53  schema-risk precheck: verdict OUTAGE, LOSSY without --accept-lossy, or a schema-risk env fault
  54  version-bump precheck: the built jar's vendorVersion is LOWER than the deployed jar's (a downgrade)
